**Status:** Abandoned — the populated six-module specification remains current product truth; this unfinished planning draft is retained as provenance, not as active launch work.

## Intent

Bring this project's living specification to a current, evidence-based state. The product documents were empty template stubs while the codebase and maintainer docs describe a mature system; the operator has also confirmed the original planning documentation was lost (CLR-002 answer), so this feature is a rebuild rather than a revision — codebase-first, with the surviving documents as corroborating remnants — and the refresh proceeds in bounded slices.

## Current Behavior

- The six required product modules under `.koolade-packet/planning/product/` contained only placeholder prose; the index invited users to "describe the project in chat to begin." (Initial slice of this feature has now populated them.)
- No active features, no open items, and no formal decision records existed (no `.koolade-packet/planning/decisions/` directory). The operator confirmed that absence reflects the loss of the previous planning documentation (CLR-002) rather than an oversight.
- Substantial evidence exists elsewhere: `README.md`, `docs/artifact-layout.md`, `docs/planner-policy.md`, `docs/chg-001-acceptance-evidence.md`, `docs/task-conversations-progress.md`, `docs/task-failure-diagnosis.md`, `docs/kool-ad-e-redesign.md`, and the module maps in `src/`.
- At filing, several references were contradictory or stale: the tagline constant versus the rebrand specification; source comments citing absent `SPECIFICATION.md` sections; decision IDs without records; and the old repository-branded product-index heading. The first three findings and their dispositions are preserved below; F9 and the public-launch cleanup resolved the index and repository identity.

## Desired Behavior

- Each of the six required concepts states current facts that can be verified in the repository, with sources; no placeholder text remains.
- Contradictions, missing decisions, and stale references surface as board items with evidence and uncertainty instead of being absorbed silently.
- Suspected quality risks are recorded as triage items with a next diagnostic step; none is treated as a confirmed defect or quietly fixed.
- Later slices deepen subsystem coverage (task generation, implementation/publication, reconciliation, harness/sandbox, time accounting) without disturbing established facts.

## Scope

- Included: populating the six required product modules from repository evidence; raising triage board items; tracking the remaining research slices in this feature.
- Excluded: modifying repository files outside Kool.ad/e-managed artifacts (README, docs/, code) — the planner is read-only and only the application applies validated document updates; creating ADRs without explicit user approval; designing new product behavior; fixing any defect; rewriting the app-maintained product index directly.

## Decisions and Assumptions

- Confirmed, reversible scope assumption (was CLR-003): "generate the documentation for this project" covers the Kool.ad/e-managed living specification — the product modules under `.koolade-packet/planning/product/`, this feature document, and the raised board items. The repository's `README.md` and `docs/` serve as verified evidence, not as rewrite targets. Evidence: (a) `docs/artifact-layout.md` states `docs/` and `SPECIFICATION.md` are "Maintainer guidance and historical references. These are project files, not Kool.ad/e's live planning store"; (b) the planning profile grants the planner only read-only repository access — only the application applies validated document updates, so the planner cannot rewrite repository files; (c) this feature's Scope section already excludes repository files outside Kool.ad/e-managed artifacts. If the operator wants README/docs/ overhauled, that is a separate operator-driven implementation task or a later feature and supersedes this assumption.
- Previous planning documentation lost; codebase-first rebuild (settled by operator answer in CLR-002): the original planning record — earlier product specification and formal decision records — was lost before this refresh began. The implementation codebase is therefore the primary evidence for every statement, and the surviving maintainer documents (`README.md`, `docs/`) are corroborating remnants, never primary authority. For enforced behavior the code is authoritative (standing policy: Rust is authority for IDs, valid transitions, routing, and validation), and any remnant-document-versus-code disagreement becomes a board item per R2 rather than being absorbed silently. This direction also disposes of the five cited-but-unrecorded decision IDs: they are reconstructed in `product:decisions` with code-plus-document provenance; note that individual files under `.koolade-packet/planning/decisions/` are minted by the application only for new durable decisions approved through planning, so the Decisions-module register is the durable record for the lost era.
- Canonical project name (settled by operator choice, CLR-001): **Kool.ad/e** is the canonical project name. Earlier planning identified the hosting repository as Packet and anticipated a rename; the public-launch decision keeps `zbarno/kool.ade` and supersedes that plan.
- Canonical brand tagline (settled by operator ruling in the CLR-004 conversation): `Drink it and get S*** done!` — S followed by three asterisks — is the product tagline, per the governing branding contract `docs/kool-ad-e-redesign.md` (including its 2026-09-29 corrections); it is used in brand lockups and splash/empty states. The internal constant `PRODUCT_TAGLINE` in `src/lib.rs` (`Project planning, made clear`) is therefore divergent as brand copy, and its rendering role is now characterized (see next bullet). The disposition of the stale `SPECIFICATION.md` section citations was settled by the operator's ruling in the CLR-004 conversation (see the following bullet).
- PRODUCT_TAGLINE rendering role (investigated Agent item, CLR-007): no examined rendering surface uses `PRODUCT_TAGLINE`. The top-bar brand moments are full-lockup embedded PNG artwork — header logo (`assets/brand/kool-ad-e-logo-transparent.png`), compact wordmark (`kool-ad-e-wordmark-transparent.png`), and splash strip — loaded via `src/ui/layout/brand.rs` and painted in `src/ui/layout/header.rs`; the lockup tagline ships inside the image, not via any string constant. The specification viewer's empty-state hint (`NO_CONTENT_HINT` in `src/ui/spec_viewer.rs`) and toast texts (caller-supplied, `src/ui/toast.rs`) do not use it either, and the examined header/menu code hardcodes its labels. Conclusion: the constant never coincides with a full-lockup brand moment under the `docs/kool-ad-e-redesign.md` placement rule, so it cannot be misread as the brand tagline where the lockup appears. Provisional reversible disposition: keep it as inert functional-chrome copy and, in a later code task, add a clarifying one-line comment (e.g., "Functional subtitle copy; the brand tagline for lockup placements per docs/kool-ad-e-redesign.md") or delete it after confirming the compiler flags it truly-unused. Dropping it preemptively is avoided until a whole-tree usage confirmation exists. Stated uncertainty: the planning sandbox in this pass provided no text-search tool, so this is a spot-check of the plausible chrome surfaces (window-header area, spec viewer, toasts, brand assets), not an exhaustive whole-tree enumeration; any undiscovered call site would flip the "droppable" branch only — the annotation remedy stays correct either way.
