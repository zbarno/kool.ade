## Problem this ticket solves and why

F-16 is owed and, verified in the tree, PiHarness::label() (src/harness/pi_harness.rs:93) has no UI caller: an operator cannot see whether pi was discovered, which binary won the PACKET_PI_BIN/PATH/common-homes race, or what version was probed, so a missing or wrong pi CLI presents as opaque interview failures instead of actionable setup steps at the moment they can be fixed (D-15).

## Ticket goal — what changes when done

Before: opening the existing settings dialog (HeaderAction::Stakeholders) shows only identity and category fields, and the harness state is invisible. After: the same card renders a 'Set up the pi harness' section whose live status line flips from a pending hint to 'pi {version}' plus the winning binary path (or an unavailable diagnostic naming the cause), with the D-13 discovery order, the PACKET_PI_BIN override semantics, the display-only version policy, and stepwise manual provision steps. Observable completion: cargo test --offline is green with the golden-text and probe-report pins, and on the operator host the section reads 'pi 0.84.4' with '/home/barnocle/.npm-global/bin/pi' after a brief pending state.

## User story

As the operator preparing my workstation for the first interview, I want the settings dialog to show me whether pi is discovered, which binary won, which version was probed, and exactly how to fix discovery, so that a missing or misplaced harness CLI is solved in seconds instead of diagnosed from opaque turn failures.

## Technical design and contracts

- New display-purpose snapshot in src/harness/pi_harness.rs: pub struct ProbeReport { pub status: String, pub diagnostic: String, pub binary: Option<std::path::PathBuf>, pub ok: bool } with pub fn PiHarness::probe_report() -> ProbeReport (panic-free, all-match arms). Construction: locate_binary() → Err(e): ok=false, binary=None, status=format!("pi (unavailable: {})", e.headline()) — BYTE-IDENTICAL to label() in the same state (parity invariant) — diagnostic=e.detail(); Ok(exe)+probe_version(exe)=Err(e): binary=Some(exe), ok=false, status same label formula, diagnostic=e.detail(); Ok(exe)+Ok(v): status=format!("pi {v}"), binary=Some(exe), ok=true, diagnostic empty. ## Edge cases and failure handling

- Trigger: pi exists but 'pi --version' times out, exits nonzero, or prints junk — required behavior: report carries binary=Some(found path) with ok=false and the failure diagnostic, so the guide shows WHICH binary was found beside why it failed; invariant: the probe is display-only and never gates connect, turns, or the save path.
- Trigger: operator rapidly opens and closes the dialog several times — required behavior: each open spawns one fresh detached probe; superseded threads finish and drop into a dead channel silently (send result ignored), bounded near-concurrency at ~2 live probes under ≤12 s each; invariant: no thread joins the UI thread, no handle accumulates.
- Trigger: $HOME unset or odd-valued at probe/compose time — required behavior: locate_binary (code) simply skips its home sites, and the composer renders literal '$HOME/<site>/pi' lines matching that reduced search; invariant: the rendered order ALWAYS mirrors COMMON_HOME_SITES plus the two preceding tiers, never a hand-typed duplicate.
- Trigger: an invalid-but-present PACKET_PI_BIN pointing at a directory or non-executable file — required behavior: rendered copy and diagnostic state 'wins outright / fails fast, no fall-through', exactly matching locate_binary's early return; invariant: the guide never over-promises a PATH rescue that the code does not perform.
- Trigger: a turn is running while the dialog is open and its probe concurrently spawns 'pi --version' — required behavior: both pi processes are independent and read-only (version probe, no session flags); the probe result is informational only and the turn's own locate/execute path is untouched; invariant: single-writer discipline and turn deadlines unaffected by the probe.
