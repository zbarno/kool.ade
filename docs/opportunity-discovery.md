# Opportunity discovery and user authority

Manager opportunity proposals are advisory. The Manager emits bounded proposals alongside its ordinary update; they are not queue work, planning goals, tasks, approvals, or permission to edit a repository. Manager v7 distinguishes evidence, inference, confidence, workaround, user value, impact, risk, and deduplication basis, and requires a citation to the target-appropriate application evidence. Its product-only scan receives an app-supplied stable target reference and public repository identity, while workspace-local repository IDs remain outside that prompt. Manager v2 through v6 prompt identities remain readable for persisted runs. Planner v3's typed request carries opportunity origin, current support evidence, workaround, user value, confidentiality class, and concrete target repository identity. Pursuing a proposal preserves its target repository ID and observed source SHA in the draft specification and Planner request; credential-bearing remote URLs are kept out of both.

## Target and evidence checks

Every proposal names a configured repository reference or the app-supplied Kool.ad/e product alias, plus the exact portable repository identity associated with it; the app resolves the product alias to its configured repository ID before persistence. `ActiveUserProject`, `KooladeProduct`, and `OtherLinkedRepository` must match those identities. The workspace Manager call receives workspace evidence and may propose only for the active project. Kool.ad/e product discovery runs as a separate Manager request in an empty app-owned temporary directory with the public product capability inventory and opportunity contract in its evidence manifest. These two source files are designated model-shareable public product documentation; they are compiled from the app build tree, so edits to them are included even before commit and must never contain local or private information. The prompt uses a synthetic scan identity, not the active workspace ID. The model cannot read either linked checkout; the application resolves the target checkout and source SHA when it persists a proposal. Cross-repository proposals must cite public evidence bound to their target; private workspace evidence is rejected during output validation and durable proposal validation. Other linked repository proposals remain unavailable until the application supplies public evidence bound to that exact target. Persisted evidence retains the source confidentiality classification. Evidence IDs must be supplied, unique, and bounded. Confidence is a closed enum, and a speculative proposal cannot claim high confidence.

A generic recipe, tool, or capability that already solves the immediate task must be considered before claiming a missing capability. A proposal should identify the current support state, workaround, duplicate check, expected benefit, tradeoffs, and a narrowly scoped approach. Model-provided severity, confidence, or proposal text never grants authority.

## User decision

The typed decision receipt binds an authenticated user ID to one opportunity ID and exact SHA-256 proposal revision. It also requires a unique receipt ID and RFC 3339 timestamp. The model output schema rejects decision and approval fields; the decision validator accepts the authenticated user identity separately from the untrusted proposal output. `Pursue` means permission to begin normal goal clarification and planning only. Plan confirmation, independent review, task execution, dependency access, and PR authorization remain separate gates.

## Decision matrix

| Observation | Propose when | Continue current work when |
| --- | --- | --- |
| A generic recipe/tool/capability exists | A native integration has evidenced reuse or user-experience benefit beyond the working recipe | The existing path satisfies the goal and no concrete additional benefit is shown |
| Repeated failure, QA defect, review finding, or spec drift | A typed finding is tied to current workspace evidence and a concrete repository target | The signal is transient, already fixed, unsupported by evidence, or duplicates an existing/rejected proposal |
| Roadmap or user-goal opportunity | The user value and likely outcome are stated, with uncertainty and tradeoffs | The idea is speculative, out of scope, or would interrupt unrelated approved work |
| Security concern | Surface urgently with its evidence and target | Never let model severity bypass the normal user-authorized repair and publishing gates |

## Current implementation and remaining integration

The prompt catalog, strict proposal validation, repository identity matching, cross-repository evidence filter, and decision receipt validator are implemented. Proposal persistence recomputes the workspace/target/problem dedup key and commits a per-UTC-day quota reservation atomically with the advisory record. The workspace-local exploration settings default to disabled and require a revision-checked explicit opt-in; scheduled exploration proposals are rejected until enabled. The daily limit is configurable from 1 to 10 proposals and applies to all origins.

The workspace Manager receives a workspace-private capability inventory derived from the validated project runtime manifest. If the inventory is missing or invalid, it is explicitly reported as unknown rather than treated as proof of missing support. It also receives recent typed lifecycle receipts and typed QA results loaded through `RuntimeQaStore::load_run`, typed implementation queue failures, provider profile mismatches, sanitized dependency broker outcomes, and unresolved product specification findings. Those signals remain workspace-local. Product discovery is a second request with no workspace summary, conversation, lifecycle records, task list, or private evidence; it runs from an empty app-owned temporary directory and receives only the designated public product capability inventory and opportunity contract under a synthetic scan identity. Its accepted evidence references are persisted as `Public`; the core opportunity validator rejects non-public evidence for other-repository targets. Event-driven workspace origins require matching application evidence IDs; arbitrary model strings do not satisfy that requirement. Dismissal is persisted as `Declined`; `Not now` is persisted as `Deferred` with a seven-day expiry, and the board offers 1, 7, or 30 day snooze actions. Repeated evidence stays suppressed. A declined proposal can be surfaced again only when new evidence arrives; a deferred proposal remains suppressed through its snooze and can be surfaced again only after expiry with new evidence. Each surfaced follow-up is a new advisory record; previous decisions remain in history. A direct user feature request continues through the normal planning flow and cannot be inferred from a model-provided opportunity origin.

For active user-project proposals, the Manager schema requires the exact workspace generic-capability inventory evidence reference in both the proposal's evidence list and support-check text. For Kool.ad/e proposals under Manager v7, it requires the public product capability inventory in both places and separately requires a reference to the opportunity contract. Earlier Manager prompt versions retain their previous contract-evidence rule. These application-generated evidence items are hash-bound and cannot be invented by proposal wording.

The durable proposal/decision flow, deduplication, quota reservation, persisted opt-in policy, settings UI, snooze controls, authenticated receipt creation, and lifecycle planning adoption are integrated. Scheduled exploration is disabled by default. When explicitly enabled, the app queues at most one exploration per seven days while the workspace is idle; the ordinary Manager path applies the configured daily proposal quota, and no implementation or planning action follows without a separate user decision. This scheduler runs through the application tick, not as a background service.
