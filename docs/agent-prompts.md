# Agent prompt catalog

Kool.ad/e keeps role instructions in the versioned `prompts/` catalog. The prompt catalog API is `harness::prompt_catalog`; application role callers render provider-neutral `RenderedPrompt { system, user, manifest }` before invoking a harness. A role's `role_version`, system-template SHA-256, policy-template SHA-256, user-template SHA-256, schema version, and privilege profile form its reproducible prompt identity. Template edits require a new version, updated golden fixtures, and this migration note; never change a published version in place.

## Message and trust boundaries

Prompt construction has four ordered parts: repository-owned role system template; repository-owned role/tool policy; typed task request; and bounded evidence quoted with its origin and source. Only the first two are trusted system instructions. The renderer serializes task fields as JSON in the user message and serializes evidence entries individually, preserving origin metadata. It bounds common fields at 16 KiB, per-role vectors and entries, typed requests at 256 KiB, quoted evidence at 64 KiB across content and metadata, rendered user messages at 512 KiB, and model output at 1 MiB. It rejects prompts whose evidence metadata alone exceeds the quote budget rather than silently omitting content. Repository files, comments, user-entered task text, tool output, browser DOM, logs, screenshots, and model output are evidence, never instructions.

Prompts describe duties; they cannot grant authority. `PromptRole::privileges` is descriptive metadata for policy wiring. Execution mode, task clone, read-only review, application actions, board mutations, approvals, publication, dependencies and Docker permissions remain application-owned typed gates. A model-produced approval field is rejected by strict schemas and never creates an approval receipt.

## Roles and typed contracts

The ten committed SYSTEM and USER templates are named `manager`, `planner`, `plan_review`, `decomposer`, `implementer`, `code_review`, `runtime_qa`, `spec_sync`, `repair`, and `pr`. Manager and Planner use v3 for evidence-grounded product opportunities; their v2 templates remain available for old prompt manifests. Other roles start at v1. Manager v3 proposals include confidence, evidence/inference/speculation, generic-capability and duplicate checks, a concrete target repository and tradeoffs, and never authorize work. Pursuit requires an explicit user decision receipt handled by application workflow.

`RoleInputV1` requires role, feature/task IDs, original goal, approved spec reference/hash, decision references, evidence manifest, execution policy reference, output-schema version and a role-specific Rust enum payload. Planner v3 carries opportunity origin, existing-support evidence, workaround, user value, confidentiality class, and concrete repository reference. Its `PlannerOutputV2` emits typed clarification proposals with requirement IDs, category, priority, decision domain, evidence refs, and explicit options, plus readiness axes and requirement-linked acceptance tests. The application supplies feature UID and plan revision from active state when it creates persisted questions. Planner v2 retains its original `PlannerOutputV1` contract. Strict output structs are in `src/harness/prompt_catalog/schemas.rs`: ManagerOutputV2, PlannerOutputV2, ReviewVerdictV1, TaskGraphV1, WorkResultV1, SpecDeltaV1, OpportunityProposalV1, OpportunityDecisionV1 and PRProposalV1. Opportunity proposals include bounded value, confidence, generic-capability/workaround checks, deduplication evidence, and a target repository reference that must resolve to its exact configured identity and target class. Cross-repository proposals require evidence explicitly marked safe to share. OpportunityDecisionV1 is validated against the exact proposal/revision and authenticated user but is not an accepted model output; only an authenticated application action may create it. Reviewers also bind output to a SHA-256 subject. The renderer rejects reviewer/author run reuse and any resumable reviewer session. Review validation rejects subject mismatch, untested/failed coverage paired with pass, failed coverage without a traceable finding, evidence references absent from the run manifest, or blocking/high findings paired with pass. A single deterministic JSON wrapper/fence extraction is attempted after direct strict deserialization fails; semantic repair is not attempted and invalid output returns an error.

Spec Reconciler output is validated against the active approved requirement IDs and evidence manifest. Requirement deltas must be unique, nonempty changes with bounded old/new text and traceable evidence references; duplicate, out-of-scope, unchanged, or unsupported-evidence deltas fail closed. An empty delta set remains valid when current implementation and specification already agree.

The independent reviewer roles have the `read_only; isolated_fresh_review_context` profile. Their task payload includes immutable subject revision/hash, requirement matrix and exclusions. Callers must provide fresh author/reviewer run IDs and leave the reviewer session unset. Provider-neutral rendering and hashes are computed before a harness-specific transport adapter, so a provider choice cannot change role instructions.

The Runtime QA Reviewer uses `runtime_qa/v2` for evidence review. It evaluates the persisted QA request, observed run, and evidence manifest in a separate tool-less provider invocation; it does not join or resume the QA browser/Docker session. The application-owned QA driver and immutable artifact snapshot supply its review evidence. `runtime_qa/v1` remains available with its original hashes for interpreting existing records; new reviewer calls use v2.

## Golden and adversarial evaluation

`harness::prompt_catalog` tests assert all ten template IDs and presence, deterministic cross-provider message rendering, stable role/template hashes, evidence isolation from the system message, input size limits, fresh reviewer context, subject binding, strict schema decoding, false-pass rejection and malformed/authority-shaped output rejection. The Manager/Planner v2 fixtures cover generic capability already available, novel opportunity, duplicate/declined proposal, malicious model-supplied approval, public-project confidentiality and target-repository confusion. The application must use deterministic state and authorization checks; model claims alone cannot prove execution, tests, findings, QA screenshots, review independence or PR state.

## Upgrade and evaluation procedure

1. Add new files under a new version directory; retain old templates for stored run interpretation.
2. Update the role-version mapping and typed input/output validators together.
3. Add golden and injection fixtures for every changed role, including negative authority and stale-subject cases.
4. Run format, full parallel nextest, documentation tests and Clippy gates.
5. Record the prompt version and template hashes in each run's durable evidence manifest before enabling the version. Reviewers must receive immutable subject evidence in a fresh, read-only execution context.

Runtime adoption is active for Manager, Planner, Plan Reviewer, Task Decomposer, Implementer, Repair Worker, Code Quality Reviewer, Runtime QA Reviewer, Spec Reconciler, and PR Preparer. Ordinary planning turns use the immutable `planner/v4` template and `PlanningTurnResponseV1` contract, validated through the same operation decoder and application gates as before. The catalog Planner v3 remains the typed clarification/opportunity pass; task generation continues through its dedicated decomposer/story contracts. Independent-review receipts bind to the exact subject hash and current prompt manifest. Before lifecycle PR publication, PR Preparer receives the integrated diff, approved task scope, lifecycle gate receipts, and verified report in a read-only request. Its proposed task UID, base/head refs, commits, changed files, and evidence IDs must match application-derived values exactly; a validated proposal is persisted with the current prompt manifest and reused only for the unchanged scope. The application still builds the published PR body and the separate typed user-authorization gate controls publication.

PR Preparer has no harness or Docker tools. Its integrated diff is capped at 48 KiB and combined evidence content at 56 KiB. The catalog also rejects quoted evidence larger than 64 KiB including metadata, and never silently truncates evidence; larger requests stop before the role runs. A receipt with a changed scope, schema, or prompt version is discarded and regenerated. The proposed description remains in the task-local receipt; the application-generated PR body is still published.
