# TaskIntent identity and record mapping

`Work` is the durable planning record created when a user starts a New Task. Its UUID is the canonical TaskIntent UID, `originalGoal` preserves the first request, `request` carries the current planning request, `kind` is the selected request type, and `key` selects the root planning conversation. New requests persist this record before the Manager turn starts. New Project onboarding uses the same identity and record path.

A root Work record stores its own `taskIntentUid`. Child planning work stores the owning root UID independently of `parentUid`: `parentUid` continues to represent the existing planning relationship, while the TaskIntent UID represents ownership. A legacy root request with no explicit link resolves to its existing Work UID without changing files during load. Explicit links must resolve to a supported root in the planning work collection.

Each TaskIntent stores an append-only list of `TaskIntentCycleV1` records. The first cycle uses the root UID and preserves the original goal. Starting a follow-up explicitly adds a new cycle UID, goal, sequence, and child planning-work record in the same revision-fenced planning-store transaction. Earlier cycle work and feature identities remain attached to their existing records; the root projection uses only the active cycle's work for current lifecycle status. A failed or replayed start cannot overwrite an already saved cycle.

Scoped decision records persist both the root UID and the cycle UID. New decisions inherit the cycle from the authenticated planning-work context. A legacy decision without a cycle may be treated as part of the original cycle only while the intent has one cycle; once follow-up cycles exist, its cycle is left unknown rather than guessed. The root event history records decision evidence, approved plan snapshot identity and hash, independent review, runtime QA, specification reconciliation, task/PR outcomes, and verified production deployment, each linked to its cycle when the source record establishes one. These entries supplement the authoritative decision and lifecycle receipts; they do not replace them.

Generated executable task metadata stores `taskIntentUid` and `taskIntentCycleUid` separately from `batchUid`, `parentTaskUid`, and `dependencyUids`. The task batch resolves both references from the planning Work record that supplied its task routing. Legacy task metadata may omit either field; migration must not guess an owner or cycle when the routing source cannot establish one.

Task chat, feature lifecycle, task lifecycle, task state, PR linkage, and execution activity remain in their existing stores and keep their existing authority. The TaskIntent identity links those records for projection; it does not turn the root into a worker session, execution lease, Git clone, or PR. Root and cycle planning conversations use distinct stable work keys; transcripts remain in the existing local task-chat store, while shared planning records retain the authored goals, linked decisions, cycle references, and append-only lifecycle history. Activity remains activity and does not create board cards by itself.

Archiving is allowed only for a type-appropriate terminal outcome in the active cycle. The shared archive timestamp and append-only archive/restore events remain on the TaskIntent root; unresolved decisions or active, awaiting-review, incomplete, or unknown child outcomes keep the request visible on the board. Starting an explicit follow-up restores the root into the board and creates a separate conversation/work cycle.

`Work.status` describes the planning request's board lane. It is not proof that a feature's approved outcome was implemented, reviewed, merged, or deployed. Aggregate TaskIntent lifecycle must use the applicable typed lifecycle and publication evidence. Missing or stale evidence remains unknown or needs attention rather than being inferred as success.
