# Self-improvement lifecycle and trust boundaries

Self-improvement is a regular Kool.ad/e feature workflow whose target is the canonical Kool.ad/e repository. An opportunity recommendation is not authorization. A persisted user Pursue decision may create a planning goal, but implementation still waits for requirement clarification, user plan confirmation, and an independent plan review. The ordinary task, claim, execution, review, runtime QA, specification reconciliation, and publication controls remain authoritative.

## Isolation and publication

Implementation runs in a task-specific clone pinned to the approved source SHA and destination branch. The executor receives only that clone and the capability required for the current task. It receives no host credentials, Docker socket, or publication authority. Self-improvement tasks ignore the global Auto Publish setting and stay held for review until an explicit PR publication action. The application never merges its own work or enables auto-merge. After a PR is ready for review, an authorized repository operator may enable GitHub auto-merge; GitHub still enforces required reviews and checks. The controller publishes through the ordinary claim-fenced Git workflow after it verifies the reviewed diff and approvals. A PR does not imply merge, installation, or activation.

The controller persists lifecycle evidence against the exact plan and implementation hashes. Optimistic revisions reject stale transitions. Before task dispatch, the controller checks the feature and lifecycle task against the persisted self-improvement run and its canonical target repository. Core task setup then verifies the resolved work uses a separate clone at the exact approved source SHA, source ref, and destination ref before the harness runs. Dispatch remains available for retries through implementation, review, QA, spec sync, and PR preparation, and rejects terminal PR and merge states. Aggregate progress advances only after every top-level task has the required implementation, review, QA, spec, and PR evidence. A closed-unmerged PR does not end the aggregate while a sibling PR remains open; the aggregate records that outcome only after all parent PRs are terminal, and returns to `PrOpened` if a parent PR is reopened. Publication, merge, installation, activation, and capability readiness are distinct states. Once every parent PR is merged to the approved destination, the controller compares each provider-reported merge commit with the latest merge commit and waits unless the provider confirms ancestry. Self-improvement plan snapshots bind a stable product `Capability ID`; this value is included in plan confirmation and carried into the run. The phases are `MergedNotActivated`, `InstalledNotActivated`, and `Activated`. After installing an authorized update, the operator explicitly confirms installation in the opportunity progress panel. The app resolves the authenticated GitHub account through `gh api user` in its sanitized, bounded probe environment and persists that account ID with the operator display identity. It accepts confirmation only when the active build identity equals the recorded merge commit; synchronization alone never marks a run installed. The installation transition upgrades the run record to schema v4, which requires the authenticated account ID while preserving replay of legacy v1-v3 records. On a later synchronization, the app loads the compiled `active-capabilities.json` inventory by stable ID and dispatches its matching registered app-owned readiness probe. The probe receipt binds the pursuing feature UID, capability ID, probe ID, inventory hash, app version, and merged commit. Missing entries, unknown probes, invalid inventory, or failed readiness checks keep the run in `InstalledNotActivated`; a matching build SHA alone is insufficient. No installer or updater is invoked. A previously blocked user-project task must separately probe its required runtime capability before resuming. This projection grants no execution, merge, or deployment permission.

`NeedsAttention` remains executable only for tasks already included in an independently reviewed plan; it cannot be entered from a PR, merge, activation, or cancelled state.

## Self-hosting threat model

The post-merge ancestry comparison uses a deduplicated background worker rather than blocking the one-second UI activity tick. Each GitHub CLI request is killed after 15 seconds. Results and failures are bound to the exact canonical remote and parent merge SHA set; failures leave the run waiting and retry after a 30-second backoff.

Treat candidate changes to authorization, provider launch, Docker policy, reviewer prompts, state persistence, and update logic as untrusted until independently reviewed and negatively tested. Candidate code cannot forge user decisions or reviewer receipts. Reviewers use fresh contexts and cannot publish. UI QA uses a separately built fixture application and isolated state, never the running user application. No linked user project is mutated while developing Kool.ad/e itself.

Opportunities discovered during an improvement remain proposals. A separate persisted Pursue decision is required for each run. Related feature/task links record the parent run and increment a persisted chain depth; the store refuses new child runs after depth two. Self-improvement work also uses a bounded concurrent-run queue so it cannot starve active user goals. User-local logs and sensitive project evidence are not copied into the public product repository or PR.

## Current model boundary

`SelfImprovementRunV1` validates the product lifecycle evidence and expected revision for each transition. Persistence, current-user confirmation, clone allocation, reviewer receipt verification, and publication use existing application-owned lifecycle services. Installation confirmation additionally requires a live authenticated GitHub account and a schema-v4 event receipt. Each parent task must have a distinct publication work item and GitHub PR number, even when equivalent URL spellings differ; opportunity details display each parent PR separately. Installation confirmation now carries the authenticated GitHub account ID returned by the bounded app-owned CLI probe, alongside the app's operator display identity and exact active build evidence; the full production feature run and independent review remain outstanding. A model response is never sufficient evidence for a lifecycle action. The deterministic local acceptance fixture covers both an unsupported-language suggestion and an unrelated keyboard-navigation improvement through persisted pursuit, review/QA/spec gates, and an isolated local Git clone. After plan approval, a fresh OS process reloads the run, records clone allocation, and exits immediately without test-harness teardown; the parent process reloads it and replays the event idempotently. The fixture then drives an isolated local clone through implementation, review, QA, spec sync, and synthetic PR publication. A second fresh OS process reloads the `PrOpened` phase and exact PR URL before merge, and the parent confirms the run is still unmerged. Implementation receipt replay remains covered by same-process store reopen. A separate headless board and store integration test follows the persisted Pursue action through lifecycle plan readiness and verifies the synchronizer stays in Planning without user and independent reviewer receipts, then reaches Ready only after both receipts and a plan-bound task are persisted. It does not allocate a clone. The test drives the real `AnswerClarification` command for a blocking approval question and verifies the answer is persisted and handed to the Manager conversation; its lifecycle question events remain synthetic. An app-level approval test now runs a deterministic independent PlanReviewer through `PlanReview::start`, production prompt/output validation, tick polling, receipt persistence, and lifecycle reconciliation. After dropping the app and reloading planner state from disk, it verifies the resulting feature is ready to decompose, the exact user and reviewer receipts are present, and no task has been generated. The harness is in-process, and the test does not cover the full clarification conversation or a real provider process. The process-boundary fixture verifies abrupt termination at clone allocation and PR publication, not full application startup/reconciliation after a crash. The active capability registry and probe fail closed on missing, malformed, mismatched, or unregistered capability evidence; a matching build SHA alone is insufficient. The production-dispatch regression now creates a verifier from persisted plan, reviewer, task, and run records; its opt-in branch uses that verifier in the app-owned rootless Docker session, confirms execution before cancellation, and confirms denial after cancellation. Fresh rootless Docker validation passed on PR head `986ae361`: the hosted full Nextest suite passed 2,523 tests with 4 skipped, and isolated Docker daemon restart recovery passed. The app synchronizer now consumes persisted CodeReviewer and RuntimeQaReviewer receipts in sequence, but the production-boundary fixture uses synthetic receipts and does not launch isolated reviewer processes or execute QA on a candidate. The app-level PR projection regression now drives persisted synthetic authorization, Opened/Merged state, operator installation confirmation, and the registered self-improvement lifecycle capability probe; it does not observe GitHub, install a real binary, or restart after installation. Provider-backed PR publication through the Evolve app and feature-specific behavioral probes for product capabilities still need production-boundary evidence; authenticated installation now has a bounded subprocess test and an app-level confirmation/reload regression that verifies authenticated account attribution and durable installed-state evidence. That test seeds the preceding lifecycle transitions, so the complete production-path Pursue-to-activation run remains unproven and #175 acceptance cannot yet be claimed.
