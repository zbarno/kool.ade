# Self-improvement lifecycle and trust boundaries

Self-improvement is a regular Kool.ad/e feature workflow whose target is the canonical Kool.ad/e repository. An opportunity recommendation is not authorization. A persisted user Pursue decision may create a planning goal, but implementation still waits for requirement clarification, user plan confirmation, and an independent plan review. The ordinary task, claim, execution, review, runtime QA, specification reconciliation, and publication controls remain authoritative.

## Isolation and publication

Implementation runs in a task-specific clone pinned to the approved source SHA and destination branch. The executor receives only that clone and the capability required for the current task. It receives no host credentials, Docker socket, or publication authority. Self-improvement tasks ignore the global Auto Publish setting and stay held for review until an explicit PR publication action; they never enable auto-merge. The controller publishes through the ordinary claim-fenced Git workflow after it verifies the reviewed diff and approvals. A PR does not imply merge, installation, or activation.

The controller persists lifecycle evidence against the exact plan and implementation hashes. Optimistic revisions reject stale transitions. Before task dispatch, the controller checks the feature and lifecycle task against the persisted self-improvement run and its canonical target repository. Core task setup then verifies the resolved work uses a separate clone at the exact approved source SHA, source ref, and destination ref before the harness runs. Dispatch remains available for retries through implementation, review, QA, spec sync, and PR preparation, and rejects terminal PR and merge states. Aggregate progress advances only after every top-level task has the required implementation, review, QA, spec, and PR evidence. A closed-unmerged PR does not end the aggregate while a sibling PR remains open; the aggregate records that outcome only after all parent PRs are terminal, and returns to `PrOpened` if a parent PR is reopened. Publication, merge, and activation are distinct states. Once every parent PR is merged to the approved destination, the controller compares each provider-reported merge commit with the latest merge commit and waits unless the provider confirms ancestry. At project synchronization, the running app embeds its build commit and version; the app-owned probe records activation only when that build commit exactly matches the aggregate merge commit. Builds without a known Git identity fail closed and remain `MergedNotActivated`. No installer or updater is invoked. This state records the running app build; a previously blocked project task must separately probe its required runtime capability before resuming. This projection grants no execution, merge, or deployment permission.

`NeedsAttention` remains executable only for tasks already included in an independently reviewed plan; it cannot be entered from a PR, merge, activation, or cancelled state.

## Self-hosting threat model

The post-merge ancestry comparison uses a deduplicated background worker rather than blocking the one-second UI activity tick. Each GitHub CLI request is killed after 15 seconds. Results and failures are bound to the exact canonical remote and parent merge SHA set; failures leave the run waiting and retry after a 30-second backoff.

Treat candidate changes to authorization, provider launch, Docker policy, reviewer prompts, state persistence, and update logic as untrusted until independently reviewed and negatively tested. Candidate code cannot forge user decisions or reviewer receipts. Reviewers use fresh contexts and cannot publish. UI QA uses a separately built fixture application and isolated state, never the running user application. No linked user project is mutated while developing Kool.ad/e itself.

Opportunities discovered during an improvement remain proposals. They cannot recursively create implementation tasks without a separate user decision. Self-improvement work uses a bounded queue so it cannot starve active user goals. User-local logs and sensitive project evidence are not copied into the public product repository or PR.

## Current model boundary

`SelfImprovementRunV1` validates the product lifecycle evidence and expected revision for each transition. Persistence, actor authentication, clone allocation, reviewer receipt verification, and publication are supplied by existing application-owned lifecycle services. A model response is never sufficient evidence for one of those actions. The deterministic local acceptance fixture covers both an unsupported-language suggestion and an unrelated keyboard-navigation improvement through persisted pursuit, review/QA/spec gates, and an isolated local Git clone. It does not exercise the desktop UI, Docker boundary, provider publication, an authorized installation receipt, or a feature-specific active-capability probe. Those production boundaries remain required before #175 acceptance can be claimed.
