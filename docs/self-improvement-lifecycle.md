# Self-improvement lifecycle and trust boundaries

Self-improvement is a regular Kool.ad/e feature workflow whose target is the canonical Kool.ad/e repository. An opportunity recommendation is not authorization. A persisted user Pursue decision may create a planning goal, but implementation still waits for requirement clarification, user plan confirmation, and an independent plan review. The ordinary task, claim, execution, review, runtime QA, specification reconciliation, and publication controls remain authoritative.

## Isolation and publication

Implementation runs in a task-specific clone pinned to the approved source SHA and destination branch. The executor receives only that clone and the capability required for the current task. It receives no host credentials, Docker socket, or publication authority. Self-improvement tasks ignore the global Auto Publish setting and stay held for review until an explicit PR publication action. The application never merges its own work or enables auto-merge. After a PR is ready for review, an authorized repository operator may enable GitHub auto-merge; GitHub still enforces required reviews and checks. The controller publishes through the ordinary claim-fenced Git workflow after it verifies the reviewed diff and approvals. A PR does not imply merge, installation, or activation.

The controller persists lifecycle evidence against the exact plan and implementation hashes. Optimistic revisions reject stale transitions. Before task dispatch, the controller checks the feature and lifecycle task against the persisted self-improvement run and its canonical target repository. Core task setup then verifies the resolved work uses a separate clone at the exact approved source SHA, source ref, and destination ref before the harness runs. Dispatch remains available for retries through implementation, review, QA, spec sync, and PR preparation, and rejects terminal PR and merge states. Aggregate progress advances only after every top-level task has the required implementation, review, QA, spec, and PR evidence. A closed-unmerged PR does not end the aggregate while a sibling PR remains open; the aggregate records that outcome only after all parent PRs are terminal, and returns to `PrOpened` if a parent PR is reopened. Publication, merge, installation, activation, and capability readiness are distinct states. Once every parent PR is merged to the approved destination, the controller compares each provider-reported merge commit with the latest merge commit and waits unless the provider confirms ancestry. Self-improvement plan snapshots bind a stable product `Capability ID`; this value is included in plan confirmation and carried into the run. The phases are `MergedNotActivated`, `InstalledNotActivated`, and `Activated`. After an operator-authorized update, the operator explicitly confirms installation in the opportunity progress panel. The app accepts that confirmation only when its build identity equals the recorded merge commit and persists the operator identity with the installation evidence; synchronization alone never marks a run installed. On a later synchronization, the app loads the compiled `active-capabilities.json` inventory by stable ID and dispatches its matching registered app-owned readiness probe. The probe receipt binds the pursuing feature UID, capability ID, probe ID, inventory hash, app version, and merged commit. Missing entries, unknown probes, invalid inventory, or failed readiness checks keep the run in `InstalledNotActivated`; a matching build SHA alone is insufficient. No installer or updater is invoked. A previously blocked user-project task must separately probe its required runtime capability before resuming. This projection grants no execution, merge, or deployment permission.

`NeedsAttention` remains executable only for tasks already included in an independently reviewed plan; it cannot be entered from a PR, merge, activation, or cancelled state.

## Self-hosting threat model

The post-merge ancestry comparison uses a deduplicated background worker rather than blocking the one-second UI activity tick. Each GitHub CLI request is killed after 15 seconds. Results and failures are bound to the exact canonical remote and parent merge SHA set; failures leave the run waiting and retry after a 30-second backoff.

Treat candidate changes to authorization, provider launch, Docker policy, reviewer prompts, state persistence, and update logic as untrusted until independently reviewed and negatively tested. Candidate code cannot forge user decisions or reviewer receipts. Reviewers use fresh contexts and cannot publish. UI QA uses a separately built fixture application and isolated state, never the running user application. No linked user project is mutated while developing Kool.ad/e itself.

Opportunities discovered during an improvement remain proposals. They cannot recursively create implementation tasks without a separate user decision. Self-improvement work uses a bounded queue so it cannot starve active user goals. User-local logs and sensitive project evidence are not copied into the public product repository or PR.

## Current model boundary

`SelfImprovementRunV1` validates the product lifecycle evidence and expected revision for each transition. Persistence, actor authentication, clone allocation, reviewer receipt verification, and publication are supplied by existing application-owned lifecycle services. A model response is never sufficient evidence for one of those actions. The deterministic local acceptance fixture covers both an unsupported-language suggestion and an unrelated keyboard-navigation improvement through persisted pursuit, review/QA/spec gates, and an isolated local Git clone. It closes and reopens the planning store after plan approval, implementation receipt, and PR creation; the implementation receipt is replayed idempotently after reopen. A separate headless board and store integration test follows the persisted Pursue action through lifecycle plan readiness and verifies the synchronizer stays in Planning without user and independent reviewer receipts, then reaches Ready only after both receipts and a plan-bound task are persisted. It does not allocate a clone. The test drives the real `AnswerClarification` command for a blocking approval question, verifies the answer is persisted and handed to the Manager conversation, and records `AnswersResolved` afterward. It still uses synthetic lifecycle events for plan readiness and does not exercise the full conversational plan-review pipeline. These are store-reopen checkpoints within one process, not OS-process restart coverage. The active capability registry and probe now fail closed on missing, malformed, mismatched, or unregistered capability evidence; a matching build SHA alone is insufficient. The fixtures still do not prove app-owned Docker execution, independent code/runtime QA, provider publication, authenticated installation, or a feature-specific behavioral probe for each product capability. Those production boundaries remain required before #175 acceptance can be claimed.
