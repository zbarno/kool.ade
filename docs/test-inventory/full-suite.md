# Full Rust test inventory

`full-suite.csv` lists the 1,936 test cases from `cargo +1.98.1 nextest list --locked --all-targets --message-format json` at `00625424e86ccb2bd9160e360b5e71981afbc52a` (`main`, 2026-10-15). Outcomes and durations come from that exact source tree's successful [CI quality run](https://github.com/zbarno/kool.ade/actions/runs/38823181402) (the CI commit has the same Git tree): 1,934 passed, 2 skipped, 0 failed. The nextest wall time was 228.243 seconds; the sum of per-case durations was 3,029.802 test-seconds and is cumulative worker time, not wall time. CI runs the suite with 16 nextest threads. The timed test command took 302.80 seconds; the complete tests and Docker runtime job took 460 seconds including setup, compilation, and teardown.

Each row records the test ID, source location and mapping method, test-name intent label, category and dependency signals, duration, result, same-name overlap candidate, and current review decision. Source locations were matched by module path for 1,870 tests. The other 66 module-path fallbacks were checked against the Rust sources: each cited line is the unique declaration of that test function name in the repository. The inventory and generator now record that mapping explicitly. This verifies locations only; category, dependency, and intent values remain name/path signals, and invariant-level overlap review is still pending. The generated intent label is the test name, not a reviewed invariant description.

Two same-name pairs (four test cases) remain and were reviewed. The two archive diagnostic cases exercise separate staging paths; the Cargo and npm cache cases exercise separate implementations. PR #215 removed two exact duplicate feature-approval test copies and kept their canonical counterparts. The removed copies summed to 23.141 test-seconds in the pre-consolidation #213 report. This current inventory does not contain those removed tests, and the available timing comparisons do not establish a full-suite wall-time reduction from their removal.

## Reviewed test overlap and removal decisions

- `app::root::board_tests::queue_execution::concurrent_workers::auto_queue_runs_independent_tasks_past_review_and_during_planning` is kept despite its 109.836-second hosted duration. This UI-to-queue E2E covers two overlapping implementations, planning chat during execution, dependency blocking while unrelated work proceeds, capacity waiting, retry after remote divergence, approval gates, publication integrity, and queue cleanup. It uses Docker, the built application binary, a fake provider, and one local Git remote reached through a synthetic `GIT_SSH_COMMAND`; it does not start an SSH server. The UI loop polls every 20 ms until completion; the fake provider adds a 300 ms execution delay and waits up to 45 seconds for the unrelated task to start before completing planning. These waits contribute to elapsed time and should be profiled before any reduction. No other reviewed case covers this combined interaction.

- The five execution::remote::protocol tests remain as direct unit coverage for bounded framing, strict envelope decoding, replay/order checks, and reconnect sequence rules. They use in-memory cursors and validators; remote-server tests cover dispatch and durable replay through different boundaries. Their source evidence and dependencies are recorded per row in full-suite.csv.
- The three `execution::remote::dependency` tests remain as in-memory validator and identity-matcher coverage for cancellation generation, credential rejection, stale response metadata, and cross-worker matching. They do not start SSH or worker processes or cover network transport and server dispatch.
- Source review reclassified the `execution::remote` scheduler, server, journal, SSH configuration, staging, worker-capacity, transport, and workspace-manifest tests as unit/component coverage. They exercise local temporary directories, synthetic backends, in-memory frames, OS threads, and local Git fixtures. None starts an SSH connection or Docker container; the separate `harness::resource_bridge::...::remote` tests retain runtime integration classifications. The reviewed rows record actual local setup dependencies and invariants in the CSV; heuristic dependency signals for unreviewed rows remain pending.

- `src/ui/theme/tests.rs::badge_impls_compile` was removed in PR #205 because it only called `badge_colors()` and discarded the returned values. Rust compilation already checks that those methods and signatures type-check; theme behavior remains covered by the palette, hue, and frame-state assertions retained in the suite.
- `src/ui/items_pane.rs::arg_shapes_compile_against_real_domain` and `partition_tracks_the_routing_law` were removed in PR #205 as copies of core routing behavior. PR #219 extended `core::routing::tests::routing_law_regression_matrix_pins_four_rules` to assert the seat-inherited partition and `recommended_next` selection. The core test is the canonical coverage for that invariant; the two UI copies were not restored.
- The three `core::repo_overview` tests remain for separate contracts: the legacy scan reports README/manifest/tree/planning-import data and enforces traversal exclusions; the managed-store scan excludes stale embedded planning artifacts; the README case enforces the configured length cap and truncation marker. Their invariant-level decisions and source evidence are recorded per row in `full-suite.csv`.
- The exact-name pairs above remain separate because they exercise distinct production paths. Their per-test rationales are recorded in `full-suite.csv`.
- `app::root::board_tests::onboarding_tests::branch_switch::two_operator_checkouts_keep_the_same_workspace_picker_and_board_after_branch_switch` remains as a shared-workspace UI integration case. It creates two operator homes with different local code branches, then proves the shared board, workspace picker, registrations, and approved feature fingerprints remain the same after one checkout switches branches. Existing tests cover individual workspace operations, but not this cross-operator branch-stability contract.
- `app::root::board_tests::onboarding_tests::zero_code::welcome_ui_creates_plans_joins_and_reopens_one_zero_code_workspace` remains as the zero-code onboarding lifecycle case. It creates a workspace and task through the UI, publishes a local planning remote, joins as a second operator, and reopens locally while retaining task identity and having no code repository. `remote_code::remote_join_shows_code_repo_tasks_and_checkout_setup_without_cloning_code` covers the separate registered-code-repository path; its remote is a local bare Git repository, not SSH transport.
- The remote-code onboarding test remains because it proves a joined operator sees a registered code-repository task without cloning the code repository, then receives actionable setup guidance when implementation is requested. Its fixture uses a local planning bare remote and synthetic code-repository metadata; it does not exercise an SSH server or remote worker. The prior inventory's SSH dependency label was inaccurate and has been corrected in the CSV.
- `core::managed_workspace::migration::tests::recovery::interrupted_migrations_resume_with_the_journaled_workspace_id` remains as a four-boundary recovery case. It injects failure after journal creation, initial commit, repository rename, and association write, then requires each recovery to keep the journaled UUID consistent across the returned workspace, manifest, association, and report. The other recovery tests cover generated identity and refusal of a modified destination. This is the same migration case retained in [the legacy migration audit](legacy-migrations-outside-implementation.md).
- `core::task_claim::tests::concurrent_verification::independent_tasks_can_verify_claims_in_the_same_planning_checkout` remains because it barrier-synchronizes verification of two independent claim leases for eight rounds in one planning checkout. Existing acquisition-race and process-fence tests cover different synchronization boundaries; sequential lease checks do not cover simultaneous verification.
- `execution::docker::backend::tests::docker_engine::stack_recipes::approved_stack_recipes_run_processes_without_claiming_qa_readiness` remains as opt-in rootless-Docker coverage for approved build, test, and start recipes across Rust, Node, Python, and Go with network denied. Review found its local `ReadyButUntested` enum self-comparison did not observe production state; this branch removes that vacuous assertion and renames the test to `approved_stack_recipes_execute_across_runtime_profiles`. `ExecutionSession::run_recipe` has no access to or mutation path for target readiness, so the integration case now asserts only the process results it actually observes.

These decisions document the specific cases reviewed for #204; they do not complete the suite-wide semantic review. Other tests remain unreviewed until their invariant and production boundary are compared with existing coverage.

The remaining 1,867 rows have no exact test-name collision; semantic overlap review is pending. A lack of name collision does not establish uniqueness.
