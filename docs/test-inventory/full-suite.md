# Full Rust test inventory

`full-suite.csv` lists the 1,940 test cases from `cargo +1.98.1 nextest list --locked --all-targets --message-format json` at `489f36af5739d933a7930efd0c0dec85ada8872d` (`main`, 2026-10-16). Outcomes and per-case durations come from successful [CI quality run 38873722485](https://github.com/zbarno/kool.ade/actions/runs/38873722485) on the identical source tree: 1,938 passed, 2 skipped, 0 failed. Its measured nextest wall time was 183.799 seconds from `time -p`; the complete tests and Docker runtime job took 401 seconds including setup, compilation, and teardown. CI runs the suite with 16 nextest threads. The earlier 307.28-second run on the prior snapshot is a separate observation, not a before/after speedup claim.

Each row records the test ID, source location and mapping method, test-name intent label, category and dependency signals, duration, result, same-name overlap candidate, and current review decision. Source locations were matched by module path for 1,874 tests; the other 66 unique-function matches were checked against the Rust sources. The inventory and generator record that mapping explicitly. This verifies locations only; category, dependency, and intent values remain name/path signals, and invariant-level overlap review is still pending. The generated intent label is the test name, not a reviewed invariant description.

Two same-name pairs (four test cases) remain and were reviewed. The two archive diagnostic cases exercise separate staging paths; the Cargo and npm cache cases exercise separate implementations. PR #215 removed two exact duplicate feature-approval test copies and kept their canonical counterparts. The removed copies summed to 23.141 test-seconds in the pre-consolidation #213 report. This current inventory does not contain those removed tests, and the available timing comparisons do not establish a full-suite wall-time reduction from their removal.

It runs a long command through controller A, executes a separate task through controller B on the same rootless Docker worker, then revokes A and proves its stale result is not applied. It requires loopback SSH, the built worker binary, rootless Docker, and local Git fixtures. The earlier failure in [run 38699416590](https://github.com/zbarno/kool.ade/actions/runs/38699416590) returned `WorkerDisconnected: Execution state could not be accessed`. At that failing revision, the event-reading handler mapped every `load_events` journal error to that same generic message, so the log cannot identify the underlying operation. A later worker-restart failure in [run 38871435851](https://github.com/zbarno/kool.ade/actions/runs/38871435851) exposed a race in that journal scan: an atomic-write temp entry could disappear between directory enumeration and metadata inspection. PR #230 filters recognized temp entries before inspecting metadata, removing that failure mode from concurrent event scans too. The shared journal-scan race is a plausible common cause of the older multi-controller failure, but the original log does not prove it. Both worker-restart and multi-controller cases passed in [run 38873722485](https://github.com/zbarno/kool.ade/actions/runs/38873722485) and again in [run 38877766654](https://github.com/zbarno/kool.ade/actions/runs/38877766654), the latter at 2.627 and 5.073 seconds respectively under rootless Docker and loopback SSH.
