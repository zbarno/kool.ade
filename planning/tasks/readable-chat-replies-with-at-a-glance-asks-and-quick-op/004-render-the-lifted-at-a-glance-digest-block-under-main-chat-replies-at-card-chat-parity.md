# 004 — Render the lifted at-a-glance digest block under Main Chat replies at card-chat parity

Feature: Readable Chat Replies with At-a-Glance Asks and Quick Option Chips (CHG-003)

Status: Individually validated; see batch index for generation status.

## Problem this ticket solves and why

Cards already float the outstanding ask (ACCENT_SOFT frame, Your-answer-needed heading, Send-answer composer), but Main Chat (chat_pane::paint at layout.rs:474) and card tabs (chat_pane::paint_task at layout.rs:445) still bury the planner's ask inside the Markdown body: after story 1 the text is shaped, yet the operator still cannot tell at a glance whether the latest reply demands a decision, what is recommended, or where the pointer points. Leaving that unread resolves nothing of the reported pain ('harder to understand what the agent needs') because the lift would exist only on secondary card chrome, not on the primary reading surface the operator actually scans.

## Ticket goal — what changes when done

After this ticket alone, any stored agent reply whose tail classifies as Digest, NextStep or FinalQuestion via the story-2 detector — and which no later user message has answered — paints, directly under its Markdown body on Main Chat, card tabs and the inline card transcript: a 1 px theme::BORDER hairline, a DIGEST_BG-tinted backdrop frame, and up to 5 bullet rows (ask first and bold), unlabeled and never truncated; 'No reply needed.' and no-marker replies paint with zero tail chrome; the card's compact frame, heading, composer and buttons stay byte-identical; legacy 'Your next step:' replies lift on Main Chat for the first time. Observable completion: egui shape-assertion tests find hairline + backdrop + bullet galleys under an open ask, find their total absence across a six-case negative battery, selector-table and card-parity tests pass, and the offline regression suite is green with zero new clippy warnings.

## User story

As the seated operator reading planner replies in Main Chat and per-card task conversations, I want the outstanding ask floated as a visually distinct block — hairline rule plus at most 5 bullets in ask, recommendation, pointer order — directly under the reply body instead of buried in the text, so I instantly see what the planner wants, what it recommends, and where to look, without scrolling or re-reading.

## Purpose

Card conversations already float the trailing ask beside Send-answer controls, but Main Chat buries the identical information inside the text wall, so the operator cannot see at a glance what the planner wants, recommends, and points at. This ticket paints the compact unlabeled digest — hairline top rule, slight backdrop or indent, ≤5 bullets ask → recommendation → pointer — as a visually distinct block directly under the Markdown-transformed body on BOTH Main Chat and card surfaces, reserving tail-block and upcoming chip tints in theme.rs; the card's existing heading plus Send-answer/Assign/Review machinery consumes the generalized detector unchanged (a one-line digest maps 1:1 to today's card behavior), 'No reply needed.' renders no chrome, no-marker replies render plain body with zero tail chrome, and legacy 'Your next step:' replies lift on Main Chat for the first time while remaining pixel-unaffected on cards.

## Technical design and contracts

- SELECTOR, extending story-2's module src/ui/reply_tail.rs: pub fn open_ask_index(messages: &[ChatMessage]) -> Option<usize>. Walk from the END with rposition for the last ChatRole::Agent message; if ANY message after that index has role User, return None (an answered ask stays answered); a System notice after it does NOT clear the lift; otherwise parse the candidate once with parse_reply_tail(&message_text::readable(msg)) and return its index only when tail.kind.asks_input(). Supporting intrinsic: impl TailKind { pub const fn asks_input(self) -> bool { matches!(self, Self::Digest | Self::NextStep | Self::FinalQuestion) } }. Pure, stateless, allocates only for the single candidate message, evaluated once per frame per pane — mirroring how split_reply is recomputed today.
- SHARED PAINTER in the same file: pub fn paint_open_ask(ui: &mut egui::Ui, tail: &ReplyTail) — early-return unless tail.kind.asks_input(). Draw order: (1) hairline ui.painter().line_segment([pt, pt + vec2(ui.available_width(), 0.0)]) at Stroke::new(1.0, theme::BORDER); (2) ui.add_space(4.0); (3) an egui::Frame::NONE.fill(theme::DIGEST_BG).corner_radius(6.0).inner_margin(Margin::symmetric(10.0, 7.0)) vertical scope; (4) rows = tail.bullets when non-empty, else the single tail.ask (covers NextStep/FinalQuestion, which carry empty bullets); each row is a horizontal scope of a theme::TEXT_DIM bullet glyph (size 13.0) plus 6 px spacing plus the row text at size 13.0, line height 20.0, color theme::TEXT, the FIRST row additionally .strong() so the ask reads as lead without printing any label word. No ellipsis anywhere: full bullet text, natural wrap at the constrained width, height bounded by the detector's 5-row maximum.
- THEME ADDITIONS in src/ui/theme.rs: pub const DIGEST_BG: Color32 = Color32::from_rgb(48, 55, 47) — a deep muted sage strictly between BG (32,32,32) and the card's answer-needed ACCENT_SOFT (66,74,64); the hairline reuses existing theme::BORDER, no new border constant. ALSO RESERVED, unused this ticket but lib-exported and dead-warning-free: pub const CHIP_FILL: Color32 = Color32::from_rgb(58, 66, 55) and pub const CHIP_BORDER: Color32 = Color32::from_rgb(96, 110, 92), doc-commented as held for CHG-003's option-chip row landing in story 5 so that widget ships theme-consistent without re-reviewing the palette.
- MAIN CHAT + CARD-TAB WIRING in src/ui/chat_pane.rs: in paint_with_hint compute let lift_at = crate::ui::reply_tail::open_ask_index(messages); ONCE before the message loop; thread a lift: bool (whether this message's index == lift_at) into the private paint_message's signature (sole caller is the loop at line 80); in the ChatRole::Agent BRANCH ONLY — where story 1 already holds shielded = message_text::readable(m) — parse let tail = parse_reply_tail(&shielded); once per message and, immediately after markdown::paint and still inside the same transparent rounded frame at the same constrained width, call if lift { paint_open_ask(ui, &tail); }. User and System branches, timestamps, ref badges, the offer card, the working strip and the composer remain byte-identical; one insertion point guarantees Main-Chat/card-tab parity by construction.
- CARD TRANSCRIPT WIRING in src/ui/task_chat.rs: in the private transcript(ui, messages) compute lift_at the same way and call paint_open_ask in the agent-role branch after the body (inside that message's existing frame). NOTHING else in task_chat.rs moves: task_chat::paint's needs_answer computation, the heading string, the ACCENT_SOFT frame fill, Stop-reply/Assign-ownership/Approve/Retry buttons, and both composer() call sites are byte-untouched — a one-bullet digest maps 1:1 onto the card's existing reply.next consumption, which the story-2 adapter-parity invariant already proves.
- EXCLUSION CONTRACTS: (a) paint_progress (live streaming chunks) is NOT wired to the painter — the lift attaches only to persisted ChatMessages, so an in-flight prefix that oscillates between Plain and Digest classification can never flicker chrome mid-stream; the block appears exactly once, atomically, when the finished reply joins the log. (b) Lifted text is provably clean: ask/bullets originate from parsing readable() output (envelope already stripped or shield-note substituted), so no JSON, braces or assistant_message key can reach the lift — asserted negatively in tests. (c) No option chips exist in this ticket; paint_open_ask's outer footprint (hairline to backdrop-frame bottom edge) is deliberately stable so story 5 appends its chip row after the same call sites without perturbing anything above it.

## Acceptance criteria

- Given a Main Chat log ending in an agent reply 'Draft ready.\n\n---\n- Which vendor shall we bind?\n- Recommended: Aurora, effective Monday.\n- Pointer: CLR-021 impact notes.', when the pane paints, then below the 'Draft ready.' body there is a 1 px BORDER-colored line segment spanning the message column, a rounded rect filled exactly DIGEST_BG, and exactly three bullet galleys in payload order with the first row carrying a stronger TextFormat than the second, and no galley text contains '---', a bare '- ' prefix, or any Ask/Recommendation/Pointer label word.
- Given that same digest reply IMMEDIATELY FOLLOWED by a User message 'Go with Aurora.', when the pane repaints, then zero shapes filled with DIGEST_BG and no associated hairline segment appear anywhere in the pane — a user answer retires the lift until a newer agent reply opens one.
- Given a stored legacy reply 'SSO is recorded.\nYour next step: Should guests use SSO too?' as the final message, when Main Chat paints it, then the lifted block renders the single line 'Should guests use SSO too.' strongly (the card-standard ask, on Main Chat for the first time), no galley contains the literal 'Your next step:', and the Markdown body still renders 'SSO is recorded.'.
- Given a final agent reply of 'SSO and MFA are confirmed.\nNo reply needed.', or marker-free 'All green, nothing blocked.', or a digest whose rule is followed by SIX bullets (degraded to Plain by the story-2 detector), when painted, then zero shapes are filled with DIGEST_BG and no extra hairline renders — plain body with absolutely no tail chrome.
- Given a card TAB (chat_pane::paint_task) whose final agent message carries the three-bullet digest, when the tab paints, then the identical hairline/backdrop/three-bullet lift appears at exact parity with Main Chat, WHILE task_chat::paint's compact card for the same key still produces the incumbent heading, ACCENT_SOFT frame fill and Send-answer composer with byte-identical logic — verified by the unmodified incumbent card tests.

## Edge cases and failure handling

- Trailing System notice: an open digest reply followed by a PM 'Update' (role System) must NOT retire the lift — clearing is user-messages-only, because a proactive system notice leaves the ask genuinely outstanding; the selector table pins both directions (system-after keeps, user-after clears).
- Mid-stream churn: while a live turn streams prefixes like 'Draft ready.\n\n--' through paint_progress, no chrome may toggle — classification of growing prefixes oscillates Plain/digest-boundary at the moment the third dash lands; excluding paint_progress from the painter makes the block appear exactly once, atomically, when the finished message joins the log.
- Double shielding on card tabs: layout.rs pre-swaps stored text to readable() output and paint_message re-applies readable(); open_ask_index must classify already-readable text identically (idempotence pinned by story 1's matrix) — a non-idempotent second application altering bullet wording would silently desync the card-tab lift from Main Chat, which the parity test mechanically catches.
- Maximum-length content: a single 240-character bullet and a five-bullet digest summing to many wrapped lines must wrap fully inside the set_width constraint with no ellipsis, scroll container, or layout blowout; detector validity bounds the block at five wrapped rows plus hairline and margins, so overflow is impossible for conforming tails.
- Detected-but-invalid shape from storage corruption: a reply whose trailing rule is followed by a non-bullet line or six bullets classifies Plain/FinalQuestion per story 2, hence paints as plain Markdown body with zero tail chrome — no partial five-of-six lift is ever painted, matching the detector's all-or-nothing invariant.
