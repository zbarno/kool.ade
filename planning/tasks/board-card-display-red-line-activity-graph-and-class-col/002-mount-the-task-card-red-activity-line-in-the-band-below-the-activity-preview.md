# 002 — Mount the task-card red activity line in the band below the activity preview

Feature: Board Card Display — Red-Line Activity Graph and Class-Colored Cards (CHG-002)

Status: Individually validated; see batch index for generation status.

## Problem this ticket solves and why

At the frozen base 28ba698 (checked out at exactly this SHA; story 1's merge tip assumed as precondition), the kanban task card still owes F-19 half-implemented: a 34 px red strip hangs above the text preview (layout.rs:527), is sized like a header gizmo, is anchored by an implicit live flag with no card-state window edge, and carries no per-card metric legend. During the long quiet stretches the operator watches, per-card slow-versus-wedged is unreadable: an active card's window drifts on a bare wall-clock tick instead of the approved minute-anchored rolling edge, and a settled card anchors on the largest sample bucket rather than the record's final-updated minute, so the promised static final window does not exist and AC 1-4 fail. Leaving it unresolved keeps the card chart decorative rather than situational.

## Ticket goal — what changes when done

After this ticket alone, every task-story card's body ends with a DANGER-red, 48 px, card-width polyline mounted directly BELOW the existing activity preview (the old 34 px top strip at :527 is removed, relocated not mirrored), whose 60-slot window is minute-aligned and card-state-derived: for a worker-running card the right edge sits at the current minute's start tick and rolls forward between repaints on a 1 s schedule; for a settled card it is frozen at the close of the record's last-updated minute (telemetry.updated_ms), permanent across repaints and relaunches. Hover on the band carries the four-part metric legend, degenerate telemetry renders a flat baseline, and task_activity::full is verified stream-only (header, timing, full post stream; no bars, no duplicate chart). Observable completion: the new in-file layout tests and one appended task_activity test pass, the full suite and clippy gates are green, and the diff is confined to layout.rs plus that one test append.

## User story

As the seated operator watching a long-running implementation ticket from the board, I want the task card's red activity line to sit in a dedicated band beneath the activity preview, roll with the clock while my worker runs, freeze at the record's final 10-minute window once it settles, and explain its metric on hover, so that I can tell slow from wedged per card without opening details or issuing poll commands.

## Purpose

With the primitive in hand, the board card still does not owe F-19: the task card mounts its graph above the compact activity preview (layout.rs task-doc branch, near the compact call), sized for the header strip, and the card is fed an implicit live-flag anchor instead of a card-state-derived window edge, leaving AC 1-4 only half-real. Mount the DANGER-red line beneath the card's existing activity preview inside the P3 bounded 40-56 px card-width band (slight card growth absorbed by the existing column scroll), advance the window's right edge between repaints for active cards, and freeze settled cards at the floor(telemetry.updated_ms/10_000) minute so the final 10-minute window stays static; give the card chart the four-part metric-meaningful hover-or-caption copy (updates per 10-second bucket, last 10 minutes, token usage is not reported, empty buckets do not mean the worker stopped), and close brief scope item 3 by verifying task_activity::full retains its header, timing line, and full scrollable post stream (chat_pane::paint_progress) with no bar or duplicate subchart, so at most one chart represents a task's activity at a time (REQ-F19-1 through REQ-F19-4, assumption P1, AC 1-5). Existing graphs on distinct surfaces are left untouched per the out-of-scope list.

## Technical design and contracts

- Add to layout.rs, grouped just above `fn board_card` (layout.rs:859): `const CARD_ACTIVITY_BAND_PX: f32 = 48.0;` (inside the P3 40-56 px band), `const CARD_ACTIVITY_HOVER: &str = "Updates per 10-second bucket · Last 10 minutes · Token usage is not reported · Empty buckets do not mean the worker stopped.";`, a pure `fn task_card_activity_anchor(active: bool, progress: Option<&crate::harness::LiveProgress>, now_ms: i64) -> i64`, and a mount seam `fn task_card_activity_band(ui: &mut egui::Ui, samples: &[(i64, u64)], active: bool, progress: Option<&crate::harness::LiveProgress>, now_ms: i64)` whose body is: `let anchor = task_card_activity_anchor(active, progress, now_ms); let response = crate::ui::task_activity::line_chart(ui, samples, anchor, theme::DANGER, egui::vec2(ui.available_width(), CARD_ACTIVITY_BAND_PX)); response.on_hover_text(CARD_ACTIVITY_HOVER); if active { ui.ctx().request_repaint_after(std::time::Duration::from_secs(1)); }` — hover is attached to the primitive's returned Response unconditionally, so the legend survives degenerate windows (REQ-F19-2), and the repaint cadence lives at the mount, not in the primitive, per story 1's contract.
- task_card_activity_anchor implements the minute-aligned window edge in ten-second ticks (6 ticks per minute): active regime returns `(now_ms / 60_000) * 6` (right edge = current minute's START, story 1's sanctioned active anchor, so the current in-progress minute is never peered into); settled regime computes `last_ms` as `progress.and_then(|p| p.telemetry.updated_ms)`, else the last sample's bucket end-proxy `samples.iter().map(|(b,_)| *b).max().map(|b| b * 10_000)` (a sample-free, stamp-free record falls back to `now_ms`), and returns `((last_ms / 60_000) + 1) * 6` — the CLOSE of the record's last-updated minute, i.e. the approved "window ending at the record's last-updated minute". The minute-CLOSE choice is deliberate: bucket b covers [b*10_000, b*10_000+9999], so minute-START alignment (x*6) would strand the final burst outside the window for any settled record (e.g. updated_ms=1_009_999 → bucket 100 sits past tick 96's right edge), while minute-CLOSE keeps every recorded sample of the final minute in view, keeps both regimes on the same 6-tick minute grid (clean roll-to-freeze snap), and makes the settled anchor a pure function of persisted record fields — identical across repaints and relaunches (AC 3 static-window guarantee).
- Restructure only the task-doc body closure in the `for doc in cards` loop: hoist `let progress = s.task_progress(&doc.path);` to the top of the closure; DELETE the line-527 `crate::ui::task_activity::graph(ui, &s.activity_samples(Some(&doc.path)), activity_active, 34.0);` statement; keep header, title button, task_conversation, add_space, and the status row byte-for-byte (the status-row ACCENT-vs-DIM color, "Assigned worker" label and compact's spinner/tag are the card-side halves of REQ-F20-2's running-versus-idle legibility and REQ-F20-3's printed-header rule, and frame hue work is story 3's); then after the existing `if let Some(progress) ... compact ... else if active { spinner + waiting label }` block, add the mount: `let samples = s.activity_samples(Some(&doc.path)); task_card_activity_band(ui, &samples, active, progress, chrono::Utc::now().timestamp_millis());` so the band is the closure's FINAL child, under the preview, on EVERY task card (present even when `progress` is None — an empty-record card still owes a flat baseline, REQ-F19-4).
- Window-roll semantics tighten deliberately: the OLD :527 call passed `activity_active` (implementation OR task-chat active) as its live flag, so chat chattering alone used to roll that strip's window and self-schedule repaints; the NEW band rolls and schedules only on `active = s.implementation_active(&doc.path)` — the worker-running state the spec ties to "the clock while a worker runs" — while the card FRAME still takes `activity_active` through the unchanged `board_card` call (frame treatment is story 3's territory). Consequence: a chat-only-active, worker-idle task card shows a frozen window, and no 1 s repaint storm is scheduled unless at least one worker is actually running; the four remaining story-1 `graph` adapter sites (:108, :501, :628, :916) keep their own live-flag behavior, signatures and hover copy untouched.
- REQ-F19-3 enforcement is verification-shaped because the bars do not exist at this revision: (a) this ticket makes ZERO non-test hunks in src/ui/task_activity.rs, so `full`'s body (header row with timing via `task_activity::timing`, "Last update Ns ago", activity label, separator, sticky ScrollArea salt "full_task_activity_stream" → `chat_pane::paint_progress`) stays byte-identical to the story-1 merge tip — confirmed by `git diff` showing task_activity.rs hunks confined to `#[cfg(test)] mod tests`; (b) one appended test there executes `full` on a fixture record and asserts the stream/timing text is present while no chart signature exists (see test_plan); (c) the card itself now hosts exactly ONE chart because :527's strip is deleted and the band is its only line-chart call, so at most one chart ever represents a task's activity per surface (card vs All-activity view).

## Edge cases and failure handling

- Trigger: worker finishes mid-observation — implementation_active flips true→false between repaints for the same card. Required behavior: the anchor regime switches from rolling current-minute-start to the record's last-updated-minute-CLOSE; because minute-CLOSE encompasses the final update's minute, the last burst remains visible and the window then holds statically with no further motion or crashes; invariant: anchor(active)=96@1_019_999 vs anchor(settled, updated_ms=1_009_999)=102 — at most a one-minute snap, same 6-tick grid.
- Trigger: task chat is active but the worker is idle (activity_active=true via task_chat_active, implementation_active=false). Required behavior: the frame's `board_card` active flag keeps receiving activity_active (visual active marking unchanged, story 3 inherits it), but the band's window does NOT roll and no 1 s repaint is scheduled — tightening the old :527 semantics where chat chatter alone advanced the metric window; invariant: window motion tracks the worker, per D-26's "while a worker runs".
- Trigger: an old relaunched record whose LiveProgress::update trimming (retain buckets ≥ newest-59) or partial serialization left samples that do not reach the settled window's left region, or whose updated_ms predates all samples by months. Required behavior: uncovered slots render as genuine measured zeros (flat line) — never extrapolated, shifted or spiked — while the anchor still derives from the persisted stamp so header/timing stay truthful; invariant: rendered occupancy equals samples ∩ [anchor-59, anchor] and the settled anchor is a pure function of record bytes.
- Trigger: extreme board compression — the per-column width floor is 190 px (layout.rs:457) but window resizing and the horizontal board scroll can still squeeze the card's inner width toward zero, and NTP can rewind the wall clock between repaints. Required behavior: available width passes through un-clamped so the card never overflows, story 1's primitive suppresses shape emission whenever the shrunken plot (shrink2 vec2(2,4)) collapses to ≤ 0, and negative/rewound epoch milliseconds cannot occur for post-1970 instants so the integer minute arithmetic stays well-defined; invariant: no NaN, no negative dimension, no inverted segments, and the 48 px vertical reservation stays constant regardless of width or clock direction.
