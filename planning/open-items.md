## CLR-026

**Priority:** High
**Authority:** Review
**Type:** Ambiguity
**Category:** Development
**Feature:** CHG-004
**Assigned To:** Development
**Status:** Open

### Question
Branch reclamation under squash (CHG-004 R3): auto-publication delivers the task as a SQUASH commit on the default branch (`git merge --squash` in the integration worktree), so the original `packet/<key>` commits are not ancestors of the published tip and `git branch -d` usually REFUSES to delete the task branch after confirmed publication. Strict R3 (ruling-faithful) keeps task branches — directories are reclaimed, but one local branch still accrues per finished task, which is half of the pain the operator reported. Option 1 — keep R3 strict to Git's `-d` (retain task branches that fail the ancestry check, record the refusal reason). Option 2 — treat the confirmed publication as the merge attestation for Packet-created task/integration branches: confirmed auto-publication (persisted candidate commit present in the remote default-branch history — a check the pipeline already performs for lost-push recovery) or a polled MERGED, combined with a clean worktree, authorizes branch deletion even where `-d` refuses on ancestry; strict `-d` still applies anywhere no such attestation exists.


### Reason
Decides whether R3 is genuinely effective and what the branch tests in AC5 assert. Option 1 risks the feature feeling inert on the branch axis (the operator's manual-pass habit persists); Option 2 deletes branches on a stronger operational attestation than raw ancestry but departs from the ruling's literal wording. Neither endangers work — the dirty/divergent rails stand — so this is a bookkeeping-aggressiveness ruling, best settled before stories hard-code branch handling.


### Recommendation
Provisional (board-reviewable): Option 2 for the attested cases — the published content demonstrably reached the remote default branch, and the ancestry check exists to protect unmerged work, of which there is none once publication is confirmed; keep strict `-d` everywhere no confirmed publication/MERGED attests (failed, attention, review states). Integration branches are unaffected either way: they fast-forward-push, so `-d` already accepts them.


### Evidence
src/core/implementation.rs: auto-publish runs `merge --squash <task_head>` in the integration worktree then one atomic fast-forward push; the task branch `packet/<key>` is created at record construction and no branch-deletion path exists anywhere in implementation.rs / implementation_queue.rs / reconciliation.rs (read-only audit). `git branch -d` semantics: refuses unless the commit is an ancestor of the merge destination — a squash descendant is not. Operator pain statement: one pair of directories PLUS local branches per finished task; manual pass after every merge/PR.
