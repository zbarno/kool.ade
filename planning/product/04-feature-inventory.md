## 4. Feature Inventory

Statuses reflect the audited v0.1.0 baseline, updated by the v1.2 landing audit.

- **F-1 Repository connection and survey** — operator attaches a git working tree; the app gathers manifests, README excerpt, and a pruned file tree as per-turn context. [implemented]
- **F-2 Interview chat** — left pane; one turn active at a time (second submit refused); cooperative Cancel; speaker-labeled chat log. [implemented]
- **F-3 Living specification view** — center, largest pane; read-only Markdown rendering; live preview streams while a turn runs. [implemented]
- **F-4 Open items panel** — right pane; priority-grouped with badges; category and assignee labels; selecting an item reveals full context; ownership gaps visually distinguished. [implemented]
- **F-5 Turn pipeline** — snapshot state; build context; assemble prompt; run pi subprocess; extract envelope; validate; apply (incl. ownership synthesis); atomic file writes; git checkpoint. [implemented]
- **F-6 Structured response contract (schema v1)** — JSON envelope with assistant_message, change_summary, updated_specification, open_items_added/updated/resolved, next_question_id; any validation failure means zero mutation (Contract §16). [implemented]
- **F-7 Item lifecycle** — four kinds (question, ambiguity, assumption, ownership); three priorities (blocking, high, normal); free-form categories routed against config; app-minted, monotonic, gap-never-reused IDs (CLR-nnn). [implemented]
- **F-8 User-scoped routing** — chat surfaces only items eligible for the current user under the D-14 routing rules (broadcast General; group membership; sole-owned personal ownership; seat inheritance for unowned roles); ownership items never enter chat; selection prefers Blocking, then earliest ID. [implemented — the full D-14 law landed with ticket 002 (PR #2, `a31bc84`): `evaluate(item, user, stakes)` decides all four branches with a regression matrix in-tree and enforcement at envelope validation (v1.2 verified)]
- **F-9 Git checkpoints** — commits staging only the touched planning paths, authored as Packet Planner; header reports branch, short SHA, dirty count, and last subject. [implemented]
- **F-10 Document import** — files copied under `planning/imports/` with sanitized POSIX/Windows-safe basenames; optional Markdown twins for LLM readability (Contract §21). [IO implemented; import dialog pending dogfood]
- **F-11 MCP passthrough** — servers listed in `.planner/mcp.json` are advertised to the pi session; the planner never brokers MCP itself (Contract §19). Audit-verified mechanism: when the file exists and is non-blank it is appended **verbatim** to every turn's prompt context under the "MCP SERVER CONFIGURATION" section (4,096-char size cap); absent or blank means "unconfigured"; the app parses no schema and passes no harness CLI argument. Authoring vehicle fixed by D-16: an in-app editor (F-18) is required at MVP — deferral to hand-editing was ruled out. [implemented — baseline plumbing plus the F-18 editor shipped with ticket 004]
- **F-12 Live feedback** — streamed snapshots of thoughts, response, spec preview, and activity line; transient by construction (never persisted, never re-fed to the prompt). [implemented]
- **F-13 Welcome / first-run guidance.** [implemented]
- **F-14 Operator-local persistence** — chat history under `$PACKET_HOME` (default `~/.packet`), per-project slugs. [implemented]
- **F-15 Configurable turn budget** — `PACKET_TURN_TIMEOUT_SECS`; the 12 h default is as-built and now RULED (`TURN_TIMEOUT` in `core/turn.rs`; D-24 ratified the as-built value, superseding D-08's original 2 h recording), evaluated at turn start, invalid values fall back (documented in README). [implemented]
- **F-16 Harness setup guide** — operator-facing documentation walking the manual provisioning of the required harness CLI(s); MVP scope covers pi only, with alternate harnesses reserved for post-MVP per the NFR-6 seam (D-12); per D-13 it covers the runtime discovery order and the `PACKET_PI_BIN` override. Vehicle fixed by D-15: in-app — a dedicated "Set up the pi harness" section inside the existing settings dialog (F-17), rendering the live discovery status (fed by `PiHarness::label()`), the discovery order, the override, and stepwise provision steps. Rendered, not per-repo-editable (a guide must not fork per repository). No standalone setup document is owed in the repository at MVP. [implemented — landed in `DlgSettings` with ticket 003 (PR #3, `c375705`); render pinned per NFR-8]
- **F-17 Planner settings dialog** — header-launched card holding the planner configuration: operator identity fields plus an editable category↔owners grid; Save atomically rewrites `.planner/config.md`, resyncs in-memory state, and commits a dedicated checkpoint (`settings: update stakeholders and identity` — exemplar live on master as `fb54229`). Parse/serialize round-trips are tolerant (both heading styles, unknown sections, empty users) and unit-tested. The manual identity fields are re-purposed per D-14: they echo the git-derived identity and act as override only when git yields nothing. Per D-15 it additionally carries the in-app F-16 setup guide section (live discovery status beside the provisioning steps). [implemented — git-identity echo/override landed with ticket 001 (FR-13) and the D-15 guide section with ticket 003; v1.2 audit confirms both live in `src/app/dialogs.rs`]
- **F-18 MCP server configuration editor** — in-app editor for `.planner/mcp.json`, required for the MVP per D-16. Modeled on the existing header-dialog pattern (a new header action opening a card in the `DlgSettings`/`DlgImport` fashion; `src/app/dialogs.rs`, header wiring in `src/app/root.rs`): a mono-space free-text field bound to the file's current contents, with an empty placeholder when no file exists. Save path: JSON well-formedness probe (syntax-only — the app deliberately does not enforce any server schema, since the consumers of the file live outside the planner, NFR-5) with an inline warning on malformed input that does not block the save; blank save ⇒ file removed ⇒ unconfigured (matching the as-built blank filter); atomic write per NFR-2; dedicated git checkpoint. Deliberately editable, unlike D-15's rendered guide: MCP configuration genuinely varies per repository. [implemented — shipped with ticket 004 (PR #4, `feedbbd`); save-path pins per NFR-8 in-tree]
- **F-19 Board-card activity line graph.** The task activity graph — observed stream update counts in ten-second buckets across the 60-slot (10-minute) rolling window held in `ActivityTelemetry.samples` (`src/harness/harness.rs`) — moves FROM the task details view (`task_activity::full()`, currently an accent-filled bar histogram, 58 px allocated) ONTO the board card's activity box (`task_activity::compact()`, which serves both the kanban card and the task-details sidebar), redrawn as a LINE chart stroked in RED in place of bars (house-red candidate: `theme::DANGER`; D-26). Carried over untouched: the sample source, peak-normalization (max count scales to full height, missing bucket = 0), the live-versus-final window derivation (window anchored to "now" while active, to the last telemetry update once finished), and the honesty caption ("Activity updates / 10s · last 10 minutes · token usage is not reported"). The details view retains the full activity stream and timing readouts minus the graph. [directed D-26 — implementation pending its story]
- **F-20 Board card type color-coding.** Every card on the mixed task board — Task-story cards (headered `{key} · Task`) and open-item cards (headered `{id} · {kind}` with kind ∈ Question / Ambiguity / Assumption / Ownership, including synthesized ownership nominations) — acquires a color treatment keyed to the card's work type so the composition of work on the board (implementation tickets versus open planning work) reads at a glance (D-27). As built, every card wears one uniform `theme::PANEL` frame with a `theme::BORDER` stroke, breaking only via the `theme::ACCENT` stroke on the active card (`board_card`, `src/ui/layout.rs`); the palette is centralized in `src/ui/theme.rs`. Typology CONFIRMED by the operator's CLR-020 answer (v1.4: "Yes card class"): the card's TYPE is the class the board already prints — the branch is structurally known at paint time (`layout.rs` board body paints item headers `{id} · {kind}` at line 273 and task headers `{key} · Task` at line 289), so NO schema, data-model, or story-format change is owed. Default hue mapping recorded (the operator offered no hue preference; planner-chosen, overridable by a word, first-class material of the F-20 story): Task-story card → `theme::ACCENT` sage (house hue, 218,223,212); each open-item class → the foreground hue its kind badge already wears from `ItemKind::badge_colors` in `theme.rs` (tested in-tree) — Question → PURPLE (167,139,250), Ambiguity → SUCCESS green (107,212,144), Assumption → lavender (190,168,255), Ownership → pink (232,145,190) — so a card frame echoes its item's own kind-badge color and the vocabulary stays coherent across panel and board. Stipulations recorded for the story: (i) the active-card marker is TODAY the ACCENT stroke, so Task's ACCENT base hue must preserve a visible active-state differentiation (heavier stroke or `ACCENT_SOFT` fill shift); (ii) `theme::DANGER` red is deliberately left UNCLAIMED as a card hue, keeping F-19's red activity line singular on the very cards that decorate; (iii) Question and Assumption share the purple family in the current badge pair — if they collapse at a glance as card frames, that is the first hue swap to make (amendment by fresh word, no re-opening of the typology ruling). [directed D-27 — typology locked v1.4 (CLR-020 resolved); implementation pending its story]
