## 2. Scope

**In scope (MVP):** single-repository desktop planner; interview chat; read-only spec rendering; open-items panel; pi harness adapter; validation-gated application of changes; git checkpoints; document import; MCP advertisement to the harness; operator-local chat persistence; tunable turn timeout; in-app harness setup guide (F-16); planner settings dialog with git-derived identity (F-17); in-app MCP server editor (F-18); board-card activity line graph (F-19); board card type color-coding (F-20) — the last two are additive board-display features directed under D-26/D-27 and change nothing in the binding §12 exit bar.

**Out of scope (Contract §24, abridged):** direct provider API integration; additional harness implementations; embedded inference; implementation-task generation; PM-tool integrations; dashboards and analytics; ADR or risk registries; review/approval workflows; spec editing in the UI; separate project database; complex permissions; autonomous coding; the D-18 WebSocket collaboration channel at MVP (phased post-MVP by D-22 — see below). (*D-12 note: supporting additional harnesses is expressed post-MVP intent; at MVP only pi is required, and the operator provisions it manually per the setup guide, F-16.* The *complex permissions* exclusion stands: D-14's exclusive/seat-inherited role model is deliberate lightweight routing, not an authorization framework — no login server, tokens, or ACL engine.)

**Platform commitment (D-11, extended).** The MVP runs on the operator's own workstation: Linux x86_64 only, built and launched from source via the local Rust toolchain. Other OS families, other Linux architectures, and any packaged/shipped distribution (installer, tarball, system package) are out of launch scope (CLR-001 resolved: "linux only", then "x86, just for this machine").

**Ruled — real-time collaboration, post-MVP phasing (D-18, D-22).** The operator directed that clients continue to persist their data in git, as designed, and that a WebSocket-based real-time channel should let others in the same repository watch and join the work live, "like Google Docs." Phasing is now RULED (D-22, resolving CLR-014): the channel ships **after** the MVP — scheduled as the first first-class post-MVP feature — and the MVP feature inventory, architecture, and binding exit criteria (§12) are frozen around its absence; the §12 walkthrough is definitively single-actor. The design successors remain open, re-ranked as prerequisites of the post-MVP channel project rather than MVP blockers: channel topology, discovery, and trust (CLR-015); writer/concurrency semantics against the single-writer spine (CLR-016); and whether the interview conversation itself crosses the wire notwithstanding D-07 (CLR-017). Ordering relative to the other post-MVP intents (additional harness backends per D-12; real-team pilot dogfood per D-20) is deliberately unset. All MVP estimates and commitments assume channel absence by ruling, not by suspense.
