# CHG-004: Post-Publication Worktree Cleanup

**Status:** Ready — planning complete. The operator signalled implementation intent in this planning conversation; per the CHG-001/CHG-002/CHG-003 precedent the operative release is the in-app **Approve feature for implementation** action registering the CHG-004 entry in the approval ledger (`.planner/workflow.json`). Ready itself confers no implementation authority.
**Directed by:** Operator ruling: stale task worktrees must be reclaimed as a terminal step of the per-task workflow (when the task's code is Done and merged), not as a separate periodic cleanup job.
**Bound:** Task-worktree resource lifecycle only. Queue semantics, locks, publication mechanics, PR polling, and reconciliation are untouched.

## Intent

Today, every completed task leaves its persistent task worktree and per-publication integration worktree (plus local branches) behind in the worktrees root, accumulating one pair of directories plus local branches per finished task. By the time of the operator's request, 21 stale worktrees had accrued in this repository's own development (later partly cleared by a manual pass). The operator's directive is to fold reclamation into the workflow: when a task reaches its terminal done state (confirmed auto-publication, or a polled PR merge mapped to completion), the workflow removes that task's worktree and integration worktree and deletes their directories. No stand-alone cleanup job is owed.

## Current Behavior

- Each task gets a stable worktree at `<connected-checkout parent>/.packet-worktrees/<project-slug>/<key>` on branch `packet/<key>`; identity persists before creation so crashed runs resume (`src/core/implementation.rs` record construction, `worktree add`, resume guards).
- Auto publication transits a per-task integration worktree: under the per-repository publication lock the pipeline fetches the latest default-branch tip and provisions a **sibling** worktree `<key>-integration-<base[:12]>` on branch `packet/integration/<key>/<base[:12]>` (reused across retries at the same base; a re-fetch at a newer base creates a fresh sibling, leaving stale per-base siblings behind), squash-merges the verified task head there, re-verifies, and publishes one atomic fast-forward commit (same file, auto-publish region; SPECIFICATION.md "Ticket implementation, recovery, and Auto mode"; product module 07 records worktree metadata under Git-private metadata).
- Nothing removes completed worktrees or branches. Code-grounded read-only audit: `src/core/implementation.rs`, `src/core/implementation_queue.rs`, and `src/core/reconciliation.rs` contain no worktree-removal or branch-deletion path — only cleanliness guards (e.g., "Worktree is not clean after verification and commit; resume to review") and an implementation prompt that forbids the agent from cleaning or resetting anything.
- The asymmetry was explicit in the docs: terminal failure keeps "its worktree and diagnosis available" (README.md, "Implement a ticket"); success had no symmetric reclamation clause. (Top-level SPECIFICATION.md and README.md now carry the added cleanup-step wording, written alongside this delta — observation, not implementation.)
- Observed consequence: at the time of the operator ruling, master's worktree list held 21 extra worktrees for already-completed tasks; the operator states a manual cleanup pass is required after every merge/PR.

## Desired Behavior

- On transition to terminal done, the workflow gains a terminal cleanup step for that task only. Candidate resolution is record- and naming-scoped — nothing is ever discovered incidentally: the task worktree, all of that task's integration siblings (`<key>-integration-<base[:12]>`, covering publication-retry residues), and the Packet-created branches `packet/<key>` and `packet/integration/<key>/<base[:12]>`. Worktrees-subtree exclusivity is operated, not assumed: before removal, each candidate is matched against a single parsed `git worktree list` snapshot at its recorded, lexically normalized path carrying its recorded branch — a worktree whose recorded branch ref has been deleted externally (still-registered residue) counts as matched only while it sits exactly at the recorded `verified_head`, and any other registration/path/branch mismatch aborts that item with a diagnostic instead of removing. A directory present at a recorded path but unregistered (or registered under another path or a live, different branch) is never touched. A candidate whose registration is already gone and whose directory is absent degenerates to registration pruning (`git worktree prune`, which strips only missing-directory registrations) plus a diagnostic, not failure. Incidental occupants of the roots (other tools, another Packet instance, manual directories) are therefore neither candidates nor removal targets.
- **Removal (operative definition, locked).** Reclamation runs a fixed, read-only-before-mutation order per candidate: registration guard → directory check → preflight predicate → unqualified `git worktree remove` → branch handling after the worktree is gone (`git branch -d` refuses branches still checked out in a registered worktree, so branch handling physically cannot lead). The preflight predicate is deterministic; a candidate is removable only if (i) **CLEAN** — `git status --porcelain` inside the worktree is empty (the same porcelain `git worktree remove` itself consults; untracked files count as dirty), (ii) **HEAD-STABLE** — `rev-parse HEAD` equals the candidate record's persisted `verified_head` (the same refusal idiom the pipeline applies at verification), and (iii) **ANCHORED** — its HEAD commit is either contained in a surviving ref (the candidate's own recorded branch qualifies, and so does any ref under refs/heads, refs/remotes, or refs/packet-*; containment is delegated to `git merge-base --is-ancestor`, the pipeline's existing lost-push probe, and is never recomputed in Packet), or the candidate's terminal-done delivery is **attested** at the recorded verified head — confirmed auto-publication (persisted `merged_commit`, status Done; the state whose durability the pipeline's recovery check reconfirms by containment) or polled-MERGED PR completion. **"Divergent" is precisely the negation of CLEAN ∧ HEAD-STABLE ∧ ANCHORED**; a dirty, head-advanced, or divergent candidate is skipped with its specific diagnostic and no mutation. Git's own refusal at unqualified `git worktree remove` (race-dirt, locked) is the **final guard**: captured as a diagnostic, never escalated — no `--force`, no manual fallback — and a refusal counts as handled, not failed. A candidate whose directory is already absent degenerates to registration pruning (`git worktree prune`, which strips only missing-directory registrations) plus diagnostic and counts as handled, not failed. Every outcome — removed, pruned, skipped, refused — is a non-fatal diagnostic: the row stays Done, confirmed publication is never rolled back or delayed, and queue advancement is unaffected.
- **Branches (locked per the CLR-026 ruling: attested deletion).** The baseline remains Git's merged check — `git branch -d`, ancestry judged entirely by Git. Because auto-publication delivers the task as a SQUASH commit, the original `packet/<key>` commits are typically not ancestors of the published tip, and strict `-d` alone would retain task branches indefinitely — reproducing half of the reported operator pain. The sweep therefore authorizes an **attested deletion** (Git's force-delete primitive confined to that single branch, i.e., `-D`) wherever strict `-d` refuses on ancestry AND all four limbs hold: **(i) RECORD-DERIVED** — the branch is the branch recorded on the candidate's own record (no incidental deletables); **(ii) DELIVERY-ATTESTED** — the task is terminal-done with confirmed auto-publication (persisted `merged_commit` + status Done; the pipeline's lost-push recovery containment already certifies the published commit sits in the remote default-branch history, so cleanup adds no network call and NFR-5 stands) or polled-MERGED PR completion; **(iii) HEAD-BOUND** — the branch's current head equals the recorded `verified_head` of the publication snapshot — any advancement past it voids the attestation; **(iv) CLEAN-SWEPT** — the branch's own worktree (task worktree for `packet/<key>`, the corresponding integration sibling for its integration branch) scanned clean and was removed by this sweep (or degenerated to pruning) under the R4 predicate. The attestation is evaluated read-only before any mutation and logged with provenance (attestation class, delivered commit, head comparison); mutation order remains attestations → worktrees → branches, so branch handling physically follows its worktree's disappearance (a branch checked out in a registered worktree is undeletable; see the CLR-028 ordering). Any branch lacking even one limb — unattested, head-voided or advanced, dirty worktree, non-terminal-done task — falls back to strict `-d`, whose refusal KEEPS the branch and records why; every branch outcome (deleted-strict, deleted-attested, kept-with-reason) is a non-fatal diagnostic, and a confirmed publication is never rolled back or delayed. The degradation property is the safety core: whenever any limb is absent or unknown, the outcome is exactly strict `-d` (the conservative Option 1), so the ruling buys reclamation without buying new loss modes. Integration branches are unaffected either way (their fast-forward-pushed heads are `-d`-clean) but ride the same unified rule.
- Safety rails: a task that is not terminal-done — in flight, waiting to merge, in review, needs attention, paused by cancellation, or terminal-failed — never loses its worktree; cleanup never force-removes a dirty or divergent worktree and never touches foreign checkouts (candidates come solely from the task's own records, and the registration-match guard above makes that verifiable per item).
- PR-mode parity: cleanup fires when polling confirms MERGED (completion). CLOSED-unmerged (attention) and REOPENED (back to review) keep the worktree, so reopening still resumes with its history. PR mode never provisions an integration worktree (it pushes the task branch directly and opens the PR via `gh` — code-verified), so PR cleanup removes only the task worktree where the candidate set is that small.
- Failure posture: a cleanup failure is a diagnostic. It leaves the worktree in place, never reverses or delays a confirmed publication, and never blocks queue advancement.

## Scope

Adds reclaim-on-done to the ticket workflow. Repository-layer documentation already carries the step wording (SPECIFICATION.md ticket section; README "Implement a ticket", written alongside this delta); product modules 05, 07, and 08 update at reconciliation. Out of scope: general Git garbage collection (reflogs, caches, object databases — including the pipeline's private `refs/packet-auto-bases/<key>` freshness cache refs), remote refs or remote branch deletion (cleanup is local-Git only — network-neutral, NFR-5 posture untouched), configurable retention policies, cleaning the originally connected checkout, worktrees owned by other tools or users, and any change to D-14 seat routing, locks, or publication serialization.

## Requirements

- R1: Auto mode — after, and only after, confirmed publication, remove the task's candidate worktrees (task worktree plus all of its integration siblings), including their directories and stale registrations.
- R2: PR mode — after polling confirms MERGED and the task maps to completion, remove the task worktree (and its integration worktrees, where ones existed for the task).
- R3 (settled by CLR-026 — attested deletion, operator-endorsed): Delete Packet-created local task/integration branches under Git's strict merged check (`git branch -d`); where strict `-d` refuses on ancestry, delete the branch via attested deletion (single-branch force delete, confined `-D`) only when the full conjunction holds — the branch is recorded on the candidate's own record ∧ the task is terminal-done with confirmed delivery (auto: persisted `merged_commit` + status Done; PR: polled MERGED) ∧ the branch head equals the recorded `verified_head` ∧ the branch's own worktree was swept clean this pass — logging attestation provenance (class, delivered commit, head). Missing any limb yields the strict `-d` outcome (keeps, records reason); no `-D` without a confirmed delivery attestation, and a head voided or advanced past the recorded head falls back to strict `-d`, which refuses unmerged advancement. Operative mechanics and the degrade-to-strict-`-d` property: Desired Behavior.
- R4: Non-terminal-done tasks and any dirty, head-advanced, or divergent worktree keep worktree and diagnosis; cleanup is skipped, never forced. Operative definition (locked in Desired Behavior): a candidate is removable only if CLEAN (empty `git status --porcelain`) ∧ HEAD-STABLE (`rev-parse HEAD` equals the record's persisted `verified_head`) ∧ ANCHORED (a surviving ref — the candidate's own recorded branch or any ref under refs/heads, refs/remotes, refs/packet-* — contains its HEAD per delegated `git merge-base --is-ancestor` probes, or its terminal-done delivery is attested at the recorded verified head via confirmed auto-publication or polled MERGED); otherwise skip with a specific diagnostic and no mutation. Git's own refusal at unqualified `git worktree remove` is the final guard — never `--force`, no manual fallback — and a refusal is a handled diagnostic outcome, not failure. A candidate whose directory is already absent degenerates to registration pruning plus diagnostic and counts as handled. Enforced exclusivity: before removing any candidate, the cleanup step confirms from a single parsed `git worktree list` snapshot that the candidate is registered at its recorded, lexically normalized path carrying its recorded branch (or, where that recorded branch ref has been deleted externally, the still-registered worktree sits exactly at the recorded `verified_head`); any other mismatch — different path, different or live, different branch, a strangled-ref worktree at any other HEAD, or a present directory with no registration — aborts that item with a diagnostic and removes nothing for it.
- R5: Cleanup failure is logged diagnostically; it does not roll back, reverse, or delay confirmed publication, nor block queue advancement.
- R6: Documentation (SPECIFICATION.md, README, modules 05/07/08) reflects the step; no new configuration knob in v1 — cleanup on done is unconditional and automatic.

## Decisions and Assumptions

- Cleanup is per-task and immediate at the done transition, rejecting the alternative batch/GC-job design per the operator ruling.
- **Settled (2026-09-21, Main Chat: "i guess story level") — task decomposition grain: story level.** The CHG-004 implementation batch is broken down into small, independently verifiable stories (the grain of the CHG-001 through CHG-003 batches: one cohesive slice per story, explicit dependencies, per-story regression evidence), not a single monolithic ticket. Administrative shaping note only — it fixes HOW the batch is carved, and changes no normative requirement or acceptance criterion above.
- Candidate derivation is scoped to the task's own recorded metadata and documented sibling naming, and the worktrees-subtree exclusivity assumption is CONFIRMED and made operable (settling the board-tracked assumption): Packet creates the root itself (`src/core/implementation.rs` builds `<parent>/.packet-worktrees/<project-slug>` and `create_dir_all`s it), the persisted `Implementation` records carry exact `worktree` paths and `branch` values for the task and each per-`(task, base)` integration record (whose state dirs `integration-<base>` enable exact sibling enumeration), and task keys embed a 16-hex FNVA1A64 fingerprint of the ticket path, making name collision with external occupants negligible. Enforcement: the pre-removal `git worktree list` registration match described in Desired Behavior / R4 — mirroring the codebase's existing identity-guard idiom (canonicalized common-dir plus `symbolic-ref` equality with "refusing to modify" errors at the resume and integration sites). Absent-directory-plus-gone-registration degenerates to `git worktree prune` plus diagnostic (prune strips only missing-directory registrations, so it cannot endanger a live external checkout); a present-but-unregistered directory always aborts.
- Branch deletion still delegates ancestry judgment to Git (`-d` semantics; Packet performs no graph math of its own). The known squash interaction — the original task-branch commits are not ancestors of the published squash tip, so strict `-d` usually refuses — is SETTLED by the CLR-026 ruling below, the single point where Packet overrides a Git refusal, and only via its own delivery-state record.
- **Settled (CLR-026) — branch reclamation under squash: attested deletion (Option 2), operator-endorsed** (delegated as "whichever is the safest option", ratified "ok option 2"). The ruling authorizes deleting `packet/<key>` and `packet/integration/<key>/<base[:12]>` beyond raw ancestry WHERE THE DELIVERY IS PROVEN at exactly the head carried, under the locked four-limb conjunction (record-derived ∧ delivery-attested ∧ head == recorded `verified_head` ∧ own worktree swept clean) — operative mechanics in Desired Behavior / R3. Safety rationale adopted: Option 1 (plain strict `-d`) guarantees the lingering per-task branch pile the operator reported, while Option 2's deletion authority demands an operational attestation STRICTER than ancestry itself (the published commit is verified in the remote default-branch history per the pipeline's recovery containment, or the platform reports MERGED) — no unmerged work can ever qualify, and any missing limb degrades the outcome to exactly strict `-d`, so worst case ≡ Option 1. Mechanics: attestations evaluated read-only before mutation; strict `-d` is always tried first; the escalatory `-D` is single-branch, issued only after the branch's worktree is gone (checked-out branches are undeletable), with provenance logged (attestation class, delivered commit, head); integration branches are unaffected either way (fast-forward-pushed heads are `-d`-clean) but share the unified rule; no new network calls at cleanup time (NFR-5 preserved).
- **Settled (CLR-028) — the R4 skip guard's operative definition is locked**, adopting the proposed predicate with the evidence-driven sharpenings below so the implementation stories stay mechanical rather than interpretive:
  - **Ordering.** `git branch -d` refuses a branch still checked out in a registered worktree, so branch handling necessarily trails worktree removal, and a candidate's own recorded branch counts as a surviving anchor at predicate time; its later consumption by `-d` (or an attested deletion) presumes the merged/publication attestation, so the anchor never silently vanishes between predicate and post-removal branch handling.
  - **Attested-delivery anchor arm.** The literal reachability-only predicate would misfire under the board's provisional squash ruling (CLR-026): auto-publication ships the task as a squash commit (`merge --squash` at `src/core/implementation.rs:1294`), so if the task branch is deleted on confirmed publication the task worktree's HEAD is contained in *no* ref and the feature would leak exactly the published worktrees the operator asked to reclaim. The terminal-done state itself — confirmed auto-publication (persisted `merged_commit` + status Done, reconfirmed by containment at `implementation.rs:1194`) or polled-MERGED completion — therefore attests removability for worktrees at the recorded `verified_head`. The arm also rescues already-stranded residue: the operator's manual passes commonly delete a published branch and forget the worktree, which would otherwise sit forever at `skipped:not-anchored`. Under the strict-`-d` ruling the kept branch anchors and this arm never fires; the wording is effective under either outcome, so it does not block the pending ruling.
  - **Externally-strangled branch edge.** The exclusivity guard treats an absent recorded branch ref as an aborting mismatch EXCEPT when the still-registered worktree at the recorded path sits exactly at the recorded `verified_head`: that one combination is recognised as our own strangled residue and proceeds to the predicate, where the attested arm (or lack of it) decides; every other absent or mismatched branch state aborts with a diagnostic. Collisions are excluded by the registration binding the recorded path plus the exact-HEAD requirement — a foreign occupant at that path cannot carry the live registration.
  - **HEAD-STABLE bound.** `rev-parse HEAD == record.verified_head` reuses the pipeline's existing refusal idiom (`implementation.rs:972–973` "Agent changed commit history…", `:1377–1383` "Integrated result changed after verification"). It binds the attestation to what was actually delivered and shields operator-added commits: a worktree whose HEAD advanced past the recorded head loses the attestation and is skipped (`skipped:head-advanced`) with its branch falling back to strict `-d`.
  - **Delegation mandate.** Every reachability judgement goes to Git: containment via the exact primitives already shipping in the pipeline (`merge-base --is-ancestor` probes at `implementation.rs:1194, :1202–1208`), refs enumerated by `git for-each-ref` narrowed to refs/heads, refs/remotes, refs/packet-*; a probe that errors counts as not-contained (conservative). Packet performs no graph math of its own.
  - **Guard equivalence.** Using the same `git status --porcelain` the removal itself consults makes a dirty-state miscategorisation at execution time impossible; execution-time refusals collapse to locked or racily-dirtied cases, which is exactly the final guard's job, and flipping locked or dirty after the predicate degrades conservatively to a captured refusal — nothing is ever lost by the preflight.
  - **Residual assumptions.** Cleanup runs serially at the terminal transition with no concurrent rework of the task's worktrees; the only unfriendly race (a simultaneously orphaned commit due to an external force-push racing the removal) is accepted residual risk under single-seated operation. The private `refs/packet-auto-bases/<key>` freshness cache refs are deliberately left behind (GC-tier bookkeeping, out of scope).
- Code-verified: PR publication never creates an integration worktree; the integration worktree is per-(task, base-commit), recreated when a publication retry's re-fetch advances the base, so stale per-base siblings must join the candidate set.
- Publication is serialized per repository and integration provisioning happens lazily under that lock, so when a task's publication is confirmed the remote tip has moved and no pending task can depend on that task's integration worktrees; defensively, cleanup skips an integration worktree still referenced by another non-done task's record.
- Remote refs are intentionally untouched; cleanup issues local Git commands only.

## Acceptance Criteria

- AC1: After confirmed auto-publication, the task worktree and integration worktree are gone (registration and directory), `git worktree list` shrinks accordingly, the board row still reads Done, and the Packet-created task/integration branches are consumed per R3 via the attested-deletion path with logged attestation.
- AC2: Equivalent result when a PR polls merged (the task branch likewise consumed per R3 under the polled-MERGED attestation); a PR that remains OPEN or closes unmerged leaves its worktree and branch intact across repeated polls.
- AC3: Cancelling, pausing, or terminally failing a mid-flight task, and later Resuming, still presents its worktree, diagnosis, and prior diffs.
- AC4: Hermetic fixture simulations drive the locked preflight predicate at done-transition with exact pass/fail expectations: S1 clean ∧ anchored (own branch intact) ⇒ `removed` — registration and directory both disappear from `git worktree list`, row still Done; S2 dirty tracked modification ⇒ `skipped:dirty`; S3 untracked-files-only dirt ⇒ `skipped:dirty`; S4 clean with HEAD contained in no ref and no attestation applying (record consistent: `verified_head` equal to the detached HEAD, no delivery state) ⇒ `skipped:not-anchored` (sub-reason no-containing-ref / no-attestation); S5 recorded directory absent while the registration remains listed (prunable) ⇒ `pruned-absent` — `git worktree prune` clears the registration, diagnostic recorded, counts as handled; S6 clean ∧ anchored but locked (`git worktree lock`) ⇒ unqualified remove attempted, Git's refusal captured as `refused:locked`, directory and registration intact, and the harness log proves no `--force` or qualifying flag was ever issued; S7 clean with HEAD advanced past the recorded `verified_head` and the branch already consumed ⇒ attestation void, `skipped:head-advanced`, intact; S8 registration still present at the recorded path but the recorded branch ref deleted externally, HEAD equal to the recorded `verified_head`, and confirmed publication persisted at that head ⇒ `removed` via the attested arm (the guard counts strangled-ref-exact-HEAD as matched), while S8′ (same, but HEAD different from the recorded `verified_head`) ⇒ guard abort with diagnostic and nothing removed. In S2, S3, S4, S7, and S8′ no `git worktree remove` is issued at all. Throughout every simulation the row stays Done, a confirmed publication is neither rolled back nor delayed, and queue advancement is unaffected.
- AC5: NFR-8 regression evidence: tests cover the happy paths (AC1–AC2), preflight-skips and final-refusal simulations (AC4), branch-kept-not-merged, attested-deletion positive and negative (a squash-delivered task branch that strict `-d` refuses on ancestry is deleted only under the full R3 conjunction, with attestation provenance logged; a missing attestation or a head advanced past the recorded `verified_head` ⇒ branch kept with recorded reason), and the registration-guard simulations (an unregistered directory at a recorded path, a candidate registered under a different live branch, and a strangled-ref worktree whose HEAD differs from the recorded `verified_head` are each aborted with a diagnostic, nothing removed); full suite green with no new clippy warnings at the pinned toolchain.
